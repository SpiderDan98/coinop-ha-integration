# No binding to a specific printer integration

Coin-op never depends on a particular printer integration. Each Device reads configurable Device Inputs (an entity, optionally one of its attributes), and an Integration Profile only pre-fills them when the printer's HA device belongs to a known integration domain. What is stored is the concrete entities and values the user confirmed, never a reference to the profile. v1 ships profiles for `anycubic` (chrisfore/anycubic_ha_local) and `anycubic_cloud` (Nino6689/hass-anycubic); every other printer, Moonraker/Rinkhals included, is mapped by hand. The same holds for every other Device Type: profiles are registered per integration, each with the Device Types it serves and a kind check that tells which of them an HA device is. `ha_washdata` (WashData), `miele` and `home_connect` each serve washing machines, dishwashers, tumble dryers, coffee machines and ovens. So do `homeconnect_ws` (Home Connect Local) and `home_connect_alt` (Home Connect Alt), the HACS integrations for Home Connect appliances, with the same Status and Program as `home_connect` and its mapping in the state values each reports. `tesla_wall_connector` serves EV chargers, and so do `evcc_intg` (evcc, per loadpoint) and `ocpp` (OCPP, per connector).

## Why

- The Kobra S1 alone has two maintained integrations, both reverse-engineered, fast-changing and single-maintainer. Binding to one would tie Coin-op's lifecycle to theirs.
- Every integration exposes a print status somehow; reading entities makes any printer work, and keeps the cost model identical for every Device.
- A profile that only pre-fills can be wrong without harm: the user sees every step and corrects it.

## Quick Start

Add Device first offers the HA devices of integrations with a profile that the profile finds a Status for and whose kind is a Device Type or can't be told (Quick Start). Picking one stores what the profile finds without walking its steps, and asks only for what no profile knows: the Device Type where the kind can't be told, the electricity meter, the electricity price and, for a Device Type with water, the water price.

- Walking every step is a lot at once for a user whose integration Coin-op already knows, and most of them accept every pre-filled step anyway.
- What is stored is unchanged: the Device Type's key and the concrete entities and values, in the shape the steps write them, never a reference to the profile or the kind it told. Reconfigure and Detect again work on such a Device as on any other.
- A wrong profile is no longer seen before it is stored. In exchange the second form names the Device Type and lists the entities found, the manual way stays one choice away, and a Run that starts or ends wrongly is corrected in the reconfigure menu.
- Nothing is guessed: a printer without a meter is sent to the manual way instead of getting an invented average power, a meter whose unit is neither energy nor power is refused, and a device whose kind its integration doesn't tell is asked its Device Type, among those the integration serves.
- The kind check only chooses what Quick Start offers and as which Device Type. Manual setup and Detect again never ask it: the Device Type the user chose is trusted, and the profile pre-fills whenever the HA device's integration serves it. A kind told wrongly therefore never blocks a Device, and a Device Type fixed at Add Device is never second-guessed later.

## Consequences

- Profiles find entities in the entity registry by unique id (of the printer's HA device and of devices linked to it via `via_device_id`, such as an ACE unit), so entities the user renamed are still found. An integration whose linked devices are Devices of their own reads the chosen HA device alone: OCPP registers each connector of a charge point with several as an HA device linked to the charge point's, so each connector is offered as an EV charger with its own Status and meter, and the charge point itself, which then has neither, is not. An integration that changes its unique ids breaks detection, not existing Devices.
- When an integration renames or replaces entities, a Device keeps pointing at the old ones until the user runs "Detect again", which re-applies the profile to Status, mapping, job, images and Program and never touches the electricity or water source or their prices (a profile may pre-fill a meter in Add Device, as Miele's per-cycle energy and water sensors).
- A profile may pre-fill a camera entity as the Thumbnail where the integration offers the job's preview as a camera rather than an image entity (Moonraker, PrusaLink). Such a camera is asked for its picture while the Run runs, never after it ended, since its state doesn't change with the picture and the preview may be empty once the job is over; a profile therefore picks a camera as Thumbnail only if it shows the current job's preview during the job. A camera that films the device is the camera input, with Snapshot, and both can be set at once. The camera entity is stored where an image entity is, so nothing stored changes.
- An EV charger profile pre-fills the charger's own energy counter as the electricity source (an Energy meter), in Add Device and Quick Start only, so Quick Start asks for nothing but the price. It takes the lifetime counter if the integration registers it and it is enabled, else the session counter: a lifetime counter avoids the meter reset Flag a session counter gets when it drops only once the next session charges, and the EV charger's per-Run meters make a session counter that restarts at 0 safe. A profile may put the session counter first where the integration's lifetime counter can't be trusted for a Run: evcc registers and enables the charger's meter also for a charger without one, where it never reports, and a profile can't tell from the registry.
- Coin-op takes nothing else from the integration: its live telemetry and its own cost sensors (hass-anycubic's job energy and cost) are ignored.
- Adding a profile is a code change in the `profiles` package: the profile in its group's module (printers, appliances, EV chargers) and the integration's entry in the shared registry; nothing in the stored data needs migrating. Its devices then show up in Quick Start by themselves.
- An integration that serves several Device Types registers every appliance with the same Status entities, so the profile alone can't tell a dishwasher from a washing machine. Its kind check tells them apart from what the integration itself registers (WashData: the kind the user picked, kept in its config entry; Miele: the appliance type it writes as the HA device's model; Home Connect, which puts no kind on the HA device: the sensors it registers for one type of appliance alone), answers "can't tell" where that says nothing (WashData's generic kinds, a Home Connect appliance without such a sensor; every appliance of Home Connect Local and Home Connect Alt, whose kind Coin-op doesn't try to tell), and "not a Device" for what is no Device Type (WashData's pump; Miele's fridges, hobs, hoods and every other model that is none of the five; a Home Connect fridge, hob or hood), which Quick Start leaves out. This replaces the earlier rule that Quick Start lists every appliance and the user picks. An integration that changes how it registers the kind makes Quick Start ask, mis-tell or leave its devices out, with manual setup still pre-filled; existing Devices don't change.
- Home Connect registers the sensors that tell the kind disabled by default, so a kind check also reads disabled entities; a Device Input must still be enabled. Only sensors it registers for the appliance's type are read, never ones that depend on what the appliance reports, and only ones Coin-op's minimum Home Assistant version registers too. A microwave has none of its own and is told by the combination of shared sensors only it has.
