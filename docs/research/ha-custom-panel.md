# Building a custom panel with persistence in a Home Assistant integration

Research for issue #3 ("Wie baut man ein eigenes Panel mit Datenhaltung in einer HA-Integration?").
Research date: 2026-11-19. Sources were read directly from primary repos at these commits:

- `home-assistant/core` `dev` @ [`3109142`](https://github.com/home-assistant/core/tree/310914243c1bdbd6149f8466ca2c8eb0cdb36d50) (abbreviated below as **core**)
- `home-assistant/frontend` `dev` @ [`9338b91`](https://github.com/home-assistant/frontend/tree/9338b91f18c746ce22bd7cc8fb44eff26909b4b6) (abbreviated as **frontend**)
- `home-assistant/developers.home-assistant` `master`, `home-assistant/supervisor` `main`, and the reference repos' default branches as of the research date.

Core line numbers refer to the commit above. The `dev` branch moves quickly, so later lines may drift slightly.

## Summary

- **Registering the panel:** call `panel_custom.async_register_panel(...)` from `async_setup_entry`. It wraps `frontend.async_register_built_in_panel(component_name="custom", ...)`. Serve the built JS bundle with `await hass.http.async_register_static_paths([StaticPathConfig(...)])`, and add a `?v=<version>` cache-buster to `module_url`. Guard against double registration on entry reload with `frontend.async_panel_exists`, and remove the panel with `frontend.async_remove_panel` on unload. Alarmo and the core KNX integration both work this way.
- **Frontend code:** write a plain Lit Web Component with a `wattbill-` prefix. It receives `hass`, `narrow`, `route` and `panel` as properties, and that is the only documented contract. Do **not** depend on HA-internal elements such as `ha-data-table`. They are not documented API, and loading them takes private router hacks (Alarmo does this). If HA components are really wanted, follow the KNX approach: pin `home-assistant/frontend` as a git submodule, bundle the components, and run the panel with `embed_iframe=True`.
- **Backend API:** use websocket commands (`@websocket_api.websocket_command` + `async_register_command`), called from the panel with `hass.callWS` / `hass.connection.subscribeMessage`. For live updates, add a `wattbill/subscribe` command that stores an unsubscribe callable in `connection.subscriptions[msg["id"]]` and pushes changes with `connection.send_event`. **Enforce authorization in the backend** with `@websocket_api.require_admin` on every mutating command. `require_admin=True` on the panel only hides it in the sidebar.
- **Persistence:** use `homeassistant.helpers.storage.Store`, with separate keys for Runs and templates, `async_delay_save`, `minor_version` plus `_async_migrate_func` for schema migrations, and `serialize_in_event_loop=False` with an immutable snapshot. Store rewrites the whole JSON file on every save and keeps everything in memory. That is fine for thousands of Runs, but it puts a ceiling on growth. Consider core's `collection.DictStorageCollection` + `DictStorageCollectionWebsocket` helper (CRUD + subscribe over websocket for free), noting that it is an undocumented helper. Do **not** use the recorder: it has no API for custom tables and purges after 10 days by default. Keep a separate SQLite file for a later "tens of thousands / querying" need, together with a `backup.py` pre/post hook.
- **Backups:** the whole config directory is backed up, `.storage/` included, minus a short exclude list (logs, `*.db-shm`, `tts/`, `.cache/`, the recorder DB optionally). Custom files under `/config/<domain>/` are therefore included. `/media` is **not** part of the HA-config backup; it is a separate, optional Supervisor folder.
- **Images:** store them under `hass.config.path("wattbill", "images", ...)` (inside `/config`, so they are backed up), keep only metadata in the Store, and serve them with your own `HomeAssistantView` (`requires_auth=True`). Uploads go over HTTP POST (multipart), not over the websocket, because aiohttp caps incoming websocket messages at 4 MiB. `<img>` cannot send an auth header, so the panel either loads images with `hass.fetchWithAuth` (and blob URLs) or uses signed paths (`auth/sign_path` from the frontend, or `async_sign_path` in the backend). Signed paths expire, and the signing secret is regenerated on every restart. Do **not** use `/config/www` (`/local/`): it is served without authentication. A `media_source` platform is optional, only for browsing images in HA's media browser.
- **Image sources:** `camera.async_get_image(hass, entity_id)` fetches the snapshot and `image.async_get_image` fetches the model thumbnail when the printer integration exposes an `image` entity. Pillow is available in core (`image_upload` pins `Pillow==13.0.0`) for thumbnailing.
- **References:** **Alarmo** (best fit: HACS integration, Lit/TS + rollup bundle committed under `frontend/dist`, `panel_custom`, Store with minor versions, websocket subscribe) and the core **KNX** panel (best practice for admin checks, subscriptions, iframe and the bundled-HA-frontend approach). **browser_mod** registers panels via `async_register_built_in_panel` directly. **HACS** registered an iframe panel up to release 2.0.5, but `main` has removed that panel code (PR #5626), so it is no longer a valid reference. **Spook, Battery Notes, Watchman and Scheduler register no panel**, but Battery Notes and Scheduler are useful references for Store migrations and websocket events.

## 1. Registering the panel, frontend ↔ backend, bundling

### 1.1 Panel registration APIs

- `panel_custom.async_register_panel(hass, frontend_url_path, webcomponent_name, sidebar_title, sidebar_icon, js_url, module_url, embed_iframe, trust_external, config, require_admin, config_panel_domain, handle_safe_area)` needs `js_url` or `module_url`. It wraps the settings into `config["_panel_custom"]` and calls `frontend.async_register_built_in_panel(component_name="custom", ...)`. Source: [core `panel_custom/__init__.py` L80-144](https://github.com/home-assistant/core/blob/310914243c1bdbd6149f8466ca2c8eb0cdb36d50/homeassistant/components/panel_custom/__init__.py#L80-L144).
- `frontend.async_register_built_in_panel(...)` raises `ValueError("Overwriting panel ...")` if the URL path already exists, unless `update=True` is passed. It then fires `EVENT_PANELS_UPDATED`. Source: [core `frontend/__init__.py` L246-283](https://github.com/home-assistant/core/blob/310914243c1bdbd6149f8466ca2c8eb0cdb36d50/homeassistant/components/frontend/__init__.py#L246-L283). Related helpers: `async_remove_panel` (L287) and `async_panel_exists` (L302) [same file](https://github.com/home-assistant/core/blob/310914243c1bdbd6149f8466ca2c8eb0cdb36d50/homeassistant/components/frontend/__init__.py#L287-L305).
- `require_admin` only filters the panel out of the `get_panels` response for non-admins ([`websocket_get_panels` L756-775](https://github.com/home-assistant/core/blob/310914243c1bdbd6149f8466ca2c8eb0cdb36d50/homeassistant/components/frontend/__init__.py#L756-L775)). It does not protect any backend endpoint. Admins can also override `require_admin`/`show_in_sidebar`/title/icon at runtime via `frontend/update_panel` ([L875-913](https://github.com/home-assistant/core/blob/310914243c1bdbd6149f8466ca2c8eb0cdb36d50/homeassistant/components/frontend/__init__.py#L875-L913)).
- `config_panel_domain=DOMAIN` links the panel to the integration: the frontend resolves the integration's config panel path from `panel.config_panel_domain` ([frontend `src/data/integration.ts` L36-41](https://github.com/home-assistant/frontend/blob/9338b91f18c746ce22bd7cc8fb44eff26909b4b6/src/data/integration.ts#L36-L41)). Alarmo uses it.
- The official doc page ([Creating custom panels](https://developers.home-assistant.io/docs/frontend/custom-ui/creating-custom-panels)) only covers the YAML `panel_custom:` variant. It documents the element properties `hass`, `narrow` and `panel` (with `panel.config`), its example also uses `route`, and it states that ES5-transpiled elements are not supported.

### 1.2 Serving the JS bundle

- `hass.http.async_register_static_paths([StaticPathConfig(url_path, path, cache_headers=True)])` ([core `http/server.py` L78-83, L434-464](https://github.com/home-assistant/core/blob/310914243c1bdbd6149f8466ca2c8eb0cdb36d50/homeassistant/components/http/server.py#L78-L83)). The old sync `register_static_path` was deprecated and scheduled for removal in 2025.7 ([dev blog 2024-06-18](https://developers.home-assistant.io/blog/2024/06/18/async_register_static_paths)).
- With `cache_headers=True`, files get `Cache-Control: public, max-age=2678400` (31 days) ([core `http/static.py` L13-15](https://github.com/home-assistant/core/blob/310914243c1bdbd6149f8466ca2c8eb0cdb36d50/homeassistant/components/http/static.py#L13-L15)), so a version or mtime query cache-buster is required. Alarmo uses `module_url=f"{PANEL_URL}?v={VERSION}&m={mtime}"` with `cache_headers=False` ([alarmo `panel.py`](https://github.com/nielsfaber/alarmo/blob/main/custom_components/alarmo/panel.py)).
- Static paths are served **without authentication**. The auth middleware only marks a request as authenticated ([core `http/auth.py` L215-250](https://github.com/home-assistant/core/blob/310914243c1bdbd6149f8466ca2c8eb0cdb36d50/homeassistant/components/http/auth.py#L215-L250)), and only `HomeAssistantView` subclasses with `requires_auth=True` (the default) reject unauthenticated requests ([core `helpers/http.py` L60-73, L136](https://github.com/home-assistant/core/blob/310914243c1bdbd6149f8466ca2c8eb0cdb36d50/homeassistant/helpers/http.py#L60-L73)). The panel JS must therefore contain no secrets. That is acceptable.
- Static routes cannot be registered twice. HACS guards re-registration on entry reload with a `hass.data` flag, commented "static paths can't be registered again when the entry reloads" ([hacs `frontend.py`](https://github.com/hacs/integration/blob/main/custom_components/hacs/frontend.py)). KNX guards the same thing with `if not async_panel_exists(hass, DOMAIN)` ([core `knx/websocket.py` L96-113](https://github.com/home-assistant/core/blob/310914243c1bdbd6149f8466ca2c8eb0cdb36d50/homeassistant/components/knx/websocket.py#L96-L113)).
- HACS packaging: everything must live in `custom_components/<domain>/`, and the version comes from GitHub *releases* (tags alone are not enough). An optional `zip_release` + `filename` in `hacs.json` lets releases ship a built zip ([HACS docs: integration](https://github.com/hacs/documentation/blob/main/source/docs/publish/integration.md), [HACS docs: start](https://github.com/hacs/documentation/blob/main/source/docs/publish/start.md)). The built JS therefore has to be committed (Alarmo commits `frontend/dist/alarm-panel.js`) or attached to a zip release.

### 1.3 How the frontend loads the panel

- Non-iframe mode: the frontend `import()`s `module_url` (or loads `js_url`), runs `document.createElement(config.name)`, sets the properties `panel`, `hass`, `narrow` and `route`, and appends the element into HA's DOM ([frontend `ha-panel-custom.ts` L217-240](https://github.com/home-assistant/frontend/blob/9338b91f18c746ce22bd7cc8fb44eff26909b4b6/src/panels/custom/ha-panel-custom.ts#L217-L240), [`load-custom-panel.ts`](https://github.com/home-assistant/frontend/blob/9338b91f18c746ce22bd7cc8fb44eff26909b4b6/src/util/custom-panel/load-custom-panel.ts), [`set-custom-panel-properties.ts`](https://github.com/home-assistant/frontend/blob/9338b91f18c746ce22bd7cc8fb44eff26909b4b6/src/util/custom-panel/set-custom-panel-properties.ts)). If the element defines `setProperties`, the frontend calls it instead.
- If the script URL's host is not `localhost`/`127.0.0.1`/the current host and `trust_external` is false, the user gets a confirm dialog ([L190-215](https://github.com/home-assistant/frontend/blob/9338b91f18c746ce22bd7cc8fb44eff26909b4b6/src/panels/custom/ha-panel-custom.ts#L190-L215)). This does not apply when the bundle is served from HA itself.
- `embed_iframe=True`: the frontend writes a same-origin iframe that loads the `custom-panel` entrypoint, which then loads the module and forwards `hass`/navigation ([`ha-panel-custom.ts` L274-280](https://github.com/home-assistant/frontend/blob/9338b91f18c746ce22bd7cc8fb44eff26909b4b6/src/panels/custom/ha-panel-custom.ts#L274-L280), [`src/entrypoints/custom-panel.ts`](https://github.com/home-assistant/frontend/blob/9338b91f18c746ce22bd7cc8fb44eff26909b4b6/src/entrypoints/custom-panel.ts)). The iframe has its own custom-element registry, so the panel can bundle any components without tag-name clashes. HACS (≤2.0.5) and KNX use the iframe mode.
- Available on `hass`: `callWS`, `callApi`, `callApiRaw`, `fetchWithAuth`, `sendWS` and `connection` ([frontend `src/types.ts` L263-303](https://github.com/home-assistant/frontend/blob/9338b91f18c746ce22bd7cc8fb44eff26909b4b6/src/types.ts#L263-L303)). Subscriptions use `conn.subscribeMessage(callback, msg)` ([home-assistant-js-websocket README](https://github.com/home-assistant/home-assistant-js-websocket/blob/master/README.md)).

### 1.4 Websocket commands, auth, live updates

- Pattern: `@websocket_api.websocket_command({...schema...})` + `@callback` or `@websocket_api.async_response`, registered with `websocket_api.async_register_command(hass, handler)`. The frontend calls it with `hass.connection.sendMessagePromise` / `callWS` ([dev docs: Extending the WebSocket API](https://developers.home-assistant.io/docs/frontend/extending/websocket-api)).
- Authorization: `@websocket_api.require_admin` raises `Unauthorized` if `connection.user` is not an admin ([core `websocket_api/decorators.py` L54-69](https://github.com/home-assistant/core/blob/310914243c1bdbd6149f8466ca2c8eb0cdb36d50/homeassistant/components/websocket_api/decorators.py#L54-L69)). There is also `ws_require_user(only_owner=..., ...)` (L72 ff.). Every websocket connection is authenticated, but **any** logged-in user, including non-admins, can call a command that has no such decorator. KNX puts `@require_admin` on essentially every command ([core `knx/websocket.py`](https://github.com/home-assistant/core/blob/310914243c1bdbd6149f8466ca2c8eb0cdb36d50/homeassistant/components/knx/websocket.py)). By contrast, I found no admin check in Alarmo's `websockets.py`, even though its panel is `require_admin=True` ([alarmo `websockets.py`](https://github.com/nielsfaber/alarmo/blob/main/custom_components/alarmo/websockets.py)). That is an example of the pitfall, not of the pattern to copy.
- HTTP views: `homeassistant.components.http.require_admin` exists as a decorator for `HomeAssistantView` methods ([core `http/decorators.py` L45 ff.](https://github.com/home-assistant/core/blob/310914243c1bdbd6149f8466ca2c8eb0cdb36d50/homeassistant/components/http/decorators.py#L45)). Core's media upload uses it ([core `media_source/local_source.py` L448-460](https://github.com/home-assistant/core/blob/310914243c1bdbd6149f8466ca2c8eb0cdb36d50/homeassistant/components/media_source/local_source.py#L448-L460)).
- Subscriptions: store an unsubscribe callable in `connection.subscriptions[msg["id"]]`, send the result once, then push with `connection.send_event(msg["id"], payload)`. HA calls all stored unsubscribes on disconnect ([core `websocket_api/connection.py` L97, L221, L332-352](https://github.com/home-assistant/core/blob/310914243c1bdbd6149f8466ca2c8eb0cdb36d50/homeassistant/components/websocket_api/connection.py#L97)). Reference implementation: `knx/subscribe_telegrams` with `async_dispatcher_connect` + `ExitStack` ([core `knx/websocket.py` L512-553](https://github.com/home-assistant/core/blob/310914243c1bdbd6149f8466ca2c8eb0cdb36d50/homeassistant/components/knx/websocket.py#L512-L553)). Alarmo uses the same idea with a payload-less "something changed" event ([alarmo `websockets.py` L60-84](https://github.com/nielsfaber/alarmo/blob/main/custom_components/alarmo/websockets.py#L60-L84)).
- Limits: a connection is closed if more than `MAX_PENDING_MSG = 4096` outbound messages queue up ([core `websocket_api/const.py` L29](https://github.com/home-assistant/core/blob/310914243c1bdbd6149f8466ca2c8eb0cdb36d50/homeassistant/components/websocket_api/const.py#L29)). HA creates `web.WebSocketResponse(heartbeat=55)` without overriding `max_msg_size` ([core `websocket_api/http.py` L103](https://github.com/home-assistant/core/blob/310914243c1bdbd6149f8466ca2c8eb0cdb36d50/homeassistant/components/websocket_api/http.py#L103)), so aiohttp's default of 4 MiB per incoming message applies ([aiohttp `web_ws.py` L104](https://github.com/aio-libs/aiohttp/blob/master/aiohttp/web_ws.py#L104)). Push deltas per Run, not full lists.
- Observation: core code at this commit uses `probatio` instead of `voluptuous` for schemas (e.g. [panel_custom L5](https://github.com/home-assistant/core/blob/310914243c1bdbd6149f8466ca2c8eb0cdb36d50/homeassistant/components/panel_custom/__init__.py#L5)), and the dev docs examples use `probatio` too. Alarmo (current HACS release line) still uses `vol`. **Uncertain:** I did not research whether `voluptuous` schemas remain accepted long term. This should be checked separately before coding.

### 1.5 Core helper for CRUD over websocket

`homeassistant.helpers.collection` provides `DictStorageCollection` (Store-backed, `async_delay_save` with `SAVE_DELAY = 10`) and `DictStorageCollectionWebsocket`. The latter auto-registers `<prefix>/list`, `/create`, `/update`, `/delete` (mutations wrapped in `require_admin`) and `/subscribe`, with an `admin_only` option for list/subscribe ([core `helpers/collection.py` L31, L369, L553-660](https://github.com/home-assistant/core/blob/310914243c1bdbd6149f8466ca2c8eb0cdb36d50/homeassistant/helpers/collection.py#L553-L660)). Core's `image_upload` builds on it ([core `image_upload/__init__.py` L67-175](https://github.com/home-assistant/core/blob/310914243c1bdbd6149f8466ca2c8eb0cdb36d50/homeassistant/components/image_upload/__init__.py#L67-L175)). **Uncertain:** the helper is not documented on developers.home-assistant.io, so it is internal API that may change, although many core integrations depend on it. It fits WattBill "templates" well. For Runs it is usable too, but `/list` returns everything in one message.

### 1.6 Bundling constraints

- The only documented contract is the element properties (§1.1) plus the websocket API. HA's own elements (`ha-data-table`, `ha-checkbox`, `ha-form`, ...) are **not documented** for custom panels, and the dev docs never mention them as API ([custom panels doc](https://developers.home-assistant.io/docs/frontend/custom-ui/creating-custom-panels)). They are lazy-loaded per HA panel. Alarmo makes them available by instantiating private router internals (`partial-panel-resolver._updateRoutes()`, `ha-panel-config.routerOptions.routes.automation.load()`) ([alarmo `load-ha-elements.ts`](https://github.com/nielsfaber/alarmo/blob/main/custom_components/alarmo/frontend/src/load-ha-elements.ts)). That is private API and can break on any frontend release (conclusion drawn from the code; no official statement found either way).
- The "official" way to reuse HA components is the KNX model: `XKNX/knx-frontend` pins `home-assistant/frontend` as a git submodule ([`.gitmodules`](https://github.com/XKNX/knx-frontend/blob/main/.gitmodules), [README](https://github.com/XKNX/knx-frontend/blob/main/README.md)), builds against it and ships the bundle as a Python package (`knx_frontend.locate_dir()`), which core serves with `embed_iframe=True` ([core `knx/websocket.py` L96-113](https://github.com/home-assistant/core/blob/310914243c1bdbd6149f8466ca2c8eb0cdb36d50/homeassistant/components/knx/websocket.py#L96-L113)). This is heavy: a large toolchain and frontend upgrades by hand.
- In non-iframe mode the panel shares the page's global `customElements` registry. Defining a tag that HA (or another custom card) already defined throws (standard Web Components behavior), so prefix all elements with `wattbill-` and avoid bundling third-party elements with generic tag names (e.g. `md-*`, `mwc-*`). HA's frontend itself uses `lit` 3.3.3 ([frontend `package.json`](https://github.com/home-assistant/frontend/blob/9338b91f18c746ce22bd7cc8fb44eff26909b4b6/package.json)). Bundling your own Lit 3 copy is what Alarmo does (`lit ^3.3.1`, rollup) ([alarmo `package.json`](https://github.com/nielsfaber/alarmo/blob/main/custom_components/alarmo/frontend/package.json)).
- For a large Run list, `@lit-labs/virtualizer` (which HA itself uses, see `package.json`) is an option for your own table.
- Theming: HA CSS custom properties (`--primary-color`, `--primary-background-color`, ...) are inherited in non-iframe mode and are also used by the iframe entrypoint ([`custom-panel.ts`](https://github.com/home-assistant/frontend/blob/9338b91f18c746ce22bd7cc8fb44eff26909b4b6/src/entrypoints/custom-panel.ts)). **Uncertain:** I found no doc that formally declares these variables stable API, but they are the de facto theming contract.

**Recommendation:** non-iframe panel, own Lit + TS bundle (rollup/vite/esbuild) committed under `custom_components/wattbill/frontend/dist/`, prefixed elements, own simple table/checkbox components, no dependency on `ha-*` elements. Talk to the backend only via `hass.callWS` / `subscribeMessage` / `fetchWithAuth`.

## 2. Persisting Runs

### 2.1 `helpers.storage.Store`

- JSON file at `<config>/.storage/<key>` ([core `helpers/storage.py` L41, `path` property](https://github.com/home-assistant/core/blob/310914243c1bdbd6149f8466ca2c8eb0cdb36d50/homeassistant/helpers/storage.py#L41)). The constructor is `Store(hass, version, key, private=False, *, atomic_writes=False, encoder=None, max_readable_version=None, minor_version=1, read_only=False, serialize_in_event_loop=True)` ([L292-347](https://github.com/home-assistant/core/blob/310914243c1bdbd6149f8466ca2c8eb0cdb36d50/homeassistant/helpers/storage.py#L292-L347)).
- Migration: on load, if `version`/`minor_version` differ, `_async_migrate_func(old_major, old_minor, data)` is called and the result is saved immediately. If only the minor version differs and the method raises `NotImplementedError`, the data is kept as is. A stored major version greater than `max_readable_version` raises `UnsupportedStorageVersionError`, which matters for downgrades ([L480-515, L660-662](https://github.com/home-assistant/core/blob/310914243c1bdbd6149f8466ca2c8eb0cdb36d50/homeassistant/helpers/storage.py#L480-L515)). Convention: bump the minor version for backward-compatible additions and the major version for breaking changes. Real-world implementations: Alarmo (`MigratableStore`, 6.3) ([alarmo `store.py`](https://github.com/nielsfaber/alarmo/blob/main/custom_components/alarmo/store.py)) and Battery Notes (1.4) ([battery_notes `store.py`](https://github.com/andrew-codechimp/HA-Battery-Notes/blob/main/custom_components/battery_notes/store.py)).
- Writes: `async_save` writes now, while `async_delay_save(data_func, delay)` coalesces writes and flushes on `EVENT_HOMEASSISTANT_FINAL_WRITE` at shutdown ([L533-615](https://github.com/home-assistant/core/blob/310914243c1bdbd6149f8466ca2c8eb0cdb36d50/homeassistant/helpers/storage.py#L533-L615)). The default write goes to a temp file followed by `os.replace` ("all or nothing", no fsync). `atomic_writes=True` adds fsync, which is documented as potentially blocking for seconds and "should only be used for mission critical files" ([core `util/file.py`](https://github.com/home-assistant/core/blob/310914243c1bdbd6149f8466ca2c8eb0cdb36d50/homeassistant/util/file.py)).
- Serialization: since late 2025 JSON serialization runs **in the event loop** by default. `serialize_in_event_loop=False` moves it (and `data_func`) to a worker thread; data must then be thread-safe. The docstring explicitly recommends this "for stores which are expected to store large amounts of data" ([L316-328](https://github.com/home-assistant/core/blob/310914243c1bdbd6149f8466ca2c8eb0cdb36d50/homeassistant/helpers/storage.py#L316-L328); [dev blog 2025-11-25](https://developers.home-assistant.io/blog/2025/11/25/storage-helper-opt-in-serialize-in-executor)).
- Volume and limits (my estimate, **not measured**): Store has no size limit, but it always loads the whole file into memory and rewrites the whole file on every (delayed) save. At about 2-5 KB JSON per Run (10-20 cost lines plus metadata, image references only), 5,000 Runs come to roughly 10-25 MB per save. With delayed saves and off-loop serialization that is acceptable, but at high edit frequency or tens of thousands of Runs, SQLite would be the more efficient choice. Mitigations: separate stores for templates/settings vs. Runs, never embed image data, and possibly shard Runs per year later (each shard its own `Store` key).

### 2.2 Separate SQLite file

- Possible with stdlib `sqlite3`, but every call must run in the executor, because blocking I/O in the event loop is flagged ([dev docs: blocking operations](https://developers.home-assistant.io/docs/asyncio_blocking_operations)). Schema migrations must be hand-rolled (e.g. `PRAGMA user_version`).
- Backup consistency: core and Supervisor tar the config directory while HA is running. The `*.db-shm` file is excluded but `*-wal` is **not** (only for the recorder DB) ([core `backup/const.py` L16-33](https://github.com/home-assistant/core/blob/310914243c1bdbd6149f8466ca2c8eb0cdb36d50/homeassistant/components/backup/const.py#L16-L33); [supervisor `homeassistant/module.py` L62-79](https://github.com/home-assistant/supervisor/blob/main/supervisor/homeassistant/module.py#L62-L79)). A live SQLite file therefore needs a `backup.py` with `async_pre_backup` (checkpoint/lock) and `async_post_backup` ([dev docs: backup platform, "Pre- and post-operations"](https://developers.home-assistant.io/docs/core/platform/backup); protocol in [core `backup/manager.py` L264-271](https://github.com/home-assistant/core/blob/310914243c1bdbd6149f8466ca2c8eb0cdb36d50/homeassistant/components/backup/manager.py#L264-L271)). The recorder does exactly this by locking its database ([core `recorder/backup.py`](https://github.com/home-assistant/core/blob/310914243c1bdbd6149f8466ca2c8eb0cdb36d50/homeassistant/components/recorder/backup.py)).

### 2.3 Recorder

Not suitable as a primary store. It records states, events and statistics, and I found no documented API for integration-owned tables. By default it purges history older than `purge_keep_days: 10` ([recorder docs](https://github.com/home-assistant/home-assistant.io/blob/current/source/_integrations/recorder.markdown)), and the DB can optionally be excluded from backups (see §2.4). It is still the right place for long-term **statistics** of WattBill sensors (e.g. cost per day), which is a separate topic.

### 2.4 What is in an HA backup

- Core backup writer: `atomic_contents_add(origin_path=hass.config.path(), arcname="data", file_filter=...)`, meaning the **whole config dir** minus `EXCLUDE_FROM_BACKUP` (`__pycache__`, `.DS_Store`, `.HA_RESTORE`, `*.db-shm`, `*.log*`, `backups/*.tar`, `tmp_backups/*.tar`, `OZW_Log.txt`, `tts/*`, `.cache/*`), plus the optional recorder DB exclusion ([core `backup/manager.py` L1973-2012](https://github.com/home-assistant/core/blob/310914243c1bdbd6149f8466ca2c8eb0cdb36d50/homeassistant/components/backup/manager.py#L1973-L2012), [`backup/const.py`](https://github.com/home-assistant/core/blob/310914243c1bdbd6149f8466ca2c8eb0cdb36d50/homeassistant/components/backup/const.py#L16-L33)). The Supervisor (HA OS) uses a nearly identical list, additionally excluding `*.corrupt.*` ([supervisor `module.py` L62-79](https://github.com/home-assistant/supervisor/blob/main/supervisor/homeassistant/module.py#L62-L79)).
- So `.storage/wattbill.*` and any `/config/wattbill/...` files **are included**.
- `/media` is a separate Supervisor folder (`Folder.MEDIA`) that the user selects optionally ([core `backup/models.py` L19-25](https://github.com/home-assistant/core/blob/310914243c1bdbd6149f8466ca2c8eb0cdb36d50/homeassistant/components/backup/models.py#L19-L25)). On Docker installs `media_dirs` defaults to `/media`, outside the config dir ([core `core_config.py` L435-440](https://github.com/home-assistant/core/blob/310914243c1bdbd6149f8466ca2c8eb0cdb36d50/homeassistant/core_config.py#L435-L440)).

**Recommendation:** use `Store` with `wattbill.runs` (major/minor versioned, `serialize_in_event_loop=False`, `async_delay_save` with a few seconds' delay, snapshot copy in `data_func`) and separate `wattbill.templates`/`wattbill.settings` stores. Keep an in-memory index (dict by run id), and send list views to the panel in paged or summarized form. Revisit SQLite only if Run counts reach the tens of thousands or querying becomes a requirement.

## 3. Storing and serving images

| Option | Auth | In backup | Assessment |
|---|---|---|---|
| `/config/www` → `/local/...` | **none**: static path, `cache_headers` on in prod ([core `frontend/__init__.py` L452-454](https://github.com/home-assistant/core/blob/310914243c1bdbd6149f8466ca2c8eb0cdb36d50/homeassistant/components/frontend/__init__.py#L452-L454)) | yes | Not recommended: publicly fetchable for anyone who can reach the instance, and it mixes into user space. |
| `media_source` platform / `/media` | `LocalMediaView` requires auth. Resolved URLs are signed for a limited time ([core `media_source/local_source.py` L385-398](https://github.com/home-assistant/core/blob/310914243c1bdbd6149f8466ca2c8eb0cdb36d50/homeassistant/components/media_source/local_source.py#L385-L398); [`media_player/browse_media.py` `async_process_play_media_url`](https://github.com/home-assistant/core/blob/310914243c1bdbd6149f8466ca2c8eb0cdb36d50/homeassistant/components/media_player/browse_media.py)) | `/media` only if the user selects it | A `media_source` platform (`async_get_media_source`, `async_resolve_media`, `async_browse_media`) ([dev docs: media source](https://developers.home-assistant.io/docs/core/platform/media_source)) is nice-to-have for browsing, but too indirect as primary storage. |
| Own `HomeAssistantView` + files in `/config/wattbill/images/` | `requires_auth=True` (default); signed paths possible | yes | **Recommended.** |

Details for the recommended option:

- Upload: `POST` multipart to e.g. `/api/wattbill/runs/{run_id}/images`, guarded by `@require_admin`. The default request body limit is 16 MiB (`MAX_CLIENT_SIZE`, [core `http/server.py` L69](https://github.com/home-assistant/core/blob/310914243c1bdbd6149f8466ca2c8eb0cdb36d50/homeassistant/components/http/server.py#L69)). Core's `image_upload` checks the content type, caps size at 10 MiB (`request._client_max_size = MAX_SIZE`, a private attribute), copies the file in the executor, and generates thumbnails with Pillow ([core `image_upload/__init__.py` L28-31, L85-127, L175-196, L249-262](https://github.com/home-assistant/core/blob/310914243c1bdbd6149f8466ca2c8eb0cdb36d50/homeassistant/components/image_upload/__init__.py#L28-L31)). This is a good template. Do not upload over the websocket because of the 4 MiB message limit (§1.4).
- Serving: in the frontend, `<img src>` cannot carry the bearer token. Two options:
  1. `hass.fetchWithAuth(path)` → `blob` → `URL.createObjectURL` ([frontend `types.ts` L276](https://github.com/home-assistant/frontend/blob/9338b91f18c746ce22bd7cc8fb44eff26909b4b6/src/types.ts#L276)).
  2. Signed paths: the panel calls websocket `auth/sign_path` (`expires` default 30 s, requires a logged-in user) ([core `auth/__init__.py` L771-793](https://github.com/home-assistant/core/blob/310914243c1bdbd6149f8466ca2c8eb0cdb36d50/homeassistant/components/auth/__init__.py#L771-L793)), or the backend returns `async_sign_path(hass, path, timedelta(...))` URLs in its websocket responses. The signature is a JWT over path and query, issued for the refresh token, and only accepted on GET/HEAD ([core `http/auth.py` L51-92, L232-238](https://github.com/home-assistant/core/blob/310914243c1bdbd6149f8466ca2c8eb0cdb36d50/homeassistant/components/http/auth.py#L51-L92)). The signing secret is `secrets.token_hex()` held in `hass.data` (L60-61), so **signed URLs become invalid after every HA restart** and must never be persisted (for example in a PDF or the Store).
- Alternative seen in core: `image_upload`'s serve view uses `requires_auth = False` and relies on unguessable IDs ([L191-196](https://github.com/home-assistant/core/blob/310914243c1bdbd6149f8466ca2c8eb0cdb36d50/homeassistant/components/image_upload/__init__.py#L191-L196)). That is simpler, but it is security by obscurity. For WattBill I recommend auth, because costs and snapshots may be private.
- Capture: camera snapshots via `homeassistant.components.camera.async_get_image(hass, entity_id, timeout=10, width=None, height=None)` ([core `camera/__init__.py` L221](https://github.com/home-assistant/core/blob/310914243c1bdbd6149f8466ca2c8eb0cdb36d50/homeassistant/components/camera/__init__.py#L221)). Model thumbnails, when the printer integration exposes an `image` entity, via `homeassistant.components.image.async_get_image` ([core `image/__init__.py` L106](https://github.com/home-assistant/core/blob/310914243c1bdbd6149f8466ca2c8eb0cdb36d50/homeassistant/components/image/__init__.py#L106)). Copy bytes to disk at Run end, because entity images change.
- Store only metadata in the Store (`id`, `kind: thumbnail|snapshot|upload`, `content_type`, `filename`, `created_at`), and delete files when a Run is deleted (in the executor).
- Pillow: core's `image_upload` pins `Pillow==13.0.0` ([manifest](https://github.com/home-assistant/core/blob/310914243c1bdbd6149f8466ca2c8eb0cdb36d50/homeassistant/components/image_upload/manifest.json)). **Uncertain:** whether a custom integration should declare its own `Pillow` requirement or rely on core's pin. Pinning a different version than core can cause conflicts.

## Open questions and uncertainties

1. Long-term status of `voluptuous` vs. `probatio` schemas for custom integrations (§1.4). Check before writing websocket schemas.
2. The `helpers.collection` storage-collection websocket helper is undocumented, internal API (§1.5).
3. HA CSS theme variables are de facto but not formally documented API (§1.6).
4. The Store size and performance figures are estimates, not measurements (§2.1). A quick benchmark with realistic Run JSON would settle this.
5. Pillow dependency handling for custom integrations (§3).
6. The HACS → core `marketplace` transition and its impact on distribution (§4).
