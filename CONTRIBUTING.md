# Contributing

## Layout

- `custom_components/coinop/`: the integration. Everything shipped to users lives here, including `translations/` (en and de, same keys) and `brand/`.
- `tests/`: backend tests, run inside a real Home Assistant test instance.
- `frontend/`: the sidebar panel (TypeScript + Lit). It builds into `custom_components/coinop/frontend/coinop-panel.js`, which is gitignored and built by CI.
- `scripts/test_ha.py`: runs the tests against the minimum, stable or beta Home Assistant release.
- `scripts/devenv.py` (with `make dev` shortcuts in the `Makefile`) and `dev/`: a local Home Assistant with test data (see [Dev container](#dev-container)).
- `scripts/release.py`: builds the release asset `coinop.zip` from a version tag (see [Release](#release)).
- `GLOSSARY.md`: domain terms; use them in code, tests and docs. Decisions go in `docs/adr/`.

### Backend modules

- `config_flow.py`: the hub entry and its options flow (`OPTIONS_SCHEMA`; `_async_validate` checks the input, e.g. the Spoolman URL against Spoolman's info endpoint; a new hub option is one field there plus its check and its `options.step.init` strings). Saving the options reloads the entry. `device_flow.py`: the Device subentry flow, one step per part of the Device's data (`device_type`, picked in Add Device's first step and never reconfigured; `printer_device_id` (the HA device of any Device Type), `status`, `mapping`, `job`, `images`, `program`, `consumption`, `price`, `water`, `water_price`). Steps are grouped into sections (`DeviceSubentryFlow._sections`, only those the Device Type's capabilities include): Add Device walks them in order, reconfigure offers them as a menu and returns to it after each; a new section is one entry there plus its menu label. The consumption and price steps are shared by every consumed quantity (`_async_meter_step`, `_async_price_entity_step`, ...; electricity keeps the plain step ids, water's are prefixed `water_`); water source none drops the `water_price` section, and a source picked in reconfigure without a price walks on to it. `profiles.py`: the Integration Profiles (`PROFILES`, by Device Type, then integration domain; ADR 0004). `detect` reads the Device's HA device and the devices linked to it (e.g. an ACE unit) from the registries and returns the sections it can fill (`status`, `mapping`, `job`, `images`, `program`, and for Miele the `consumption` and `water` meters), matching entities by unique id suffix; only the profiles of the Device's Type are tried. Add Device starts from them, and reconfigure's "Detect again" (offered only when `detect` knows the device) walks those sections pre-filled with them, except the meters (`METERS`), which it never touches. A new profile is one function there. `device_config.py` reads that data into a `DeviceConfig` and holds each Device Type's capability set (`CAPABILITIES`: `Capability` job inputs, images, Material, Part Count, average power, Program, Doses, water, Program consumption (electricity and water source "per Program"), per-Run meters (meters that count each Run from 0, so a drop after its end is no `meter_reset`); code branches on these, never on the type name, and `coinop/devices/list` sends them to the panel as `capabilities`); `device_inputs.py` reads Device Inputs from HA states and the entity registry, including a quantity's meter or rate readings converted to its units (`meter_reading`, e.g. kWh or W, units via HA's unit converters, else the user's conversion factor) and prices converted to `<currency>` per its unit (`price_reading`; `price_scale` understands the currency's code or symbol and sub-units like ct ÷ 100, per Wh/kWh/MWh). `quantities.py`: the consumed quantities (`Quantity`: Line Item kind, units of its meter and rate input, the unit prices are entered and shown in (`price_unit`, e.g. m³ for water priced per L) and a price entity's units (`price_units`), the Device's section keys, its Program Defaults column (`default_key`) and display decimals; `QUANTITIES` by Line Item kind); `ELECTRICITY` and `WATER` (meter in L, flow in L/min; Devices with the `water` Capability).
- `models.py`: `Run` and `LineItem`, free of HA types, with the JSON shape the Stores keep (`as_dict` / `from_dict`). A Run keeps a `Timeline` per consumed quantity (`Run.timelines`, by Line Item kind): the source section it started with (so a source change applies from the next Run), the price section it follows and, until finalised, its meter's `readings` and its `prices`. A Line Item's `quantity`, `unit_price` and `amount` are what counts; `LineItem.override` takes the user's values (an amount back-computes the unit price) and, on a computed Line Item (`is_computed`), keeps Coin-op's values in `computed` until `reset`. Which Line Items are live (`Run.locked`: computed ones until the Run is final), deletable (`Run.deletable`) and allow negative prices (`negative_prices`) is decided there too, A Dose's Material Line Item carries `dose_id` and `dose_source` (written only on those; `LineItem.from_defaults` marks a Water or Dose amount defaulted for a whole Run), and is computed like electricity. Which Flags a correction fixed (`Run.drop_fixed_flags`: `usage_missing` once every Material Line Item has a quantity, `material_missing` once each has a Material); `websocket/line_items.py` (`coinop/line_items/update`, `reset`, `add`, `delete`) applies these rules.
- `materials.py`: `Material`, free of HA types, with its built-in types (`MATERIAL_TYPES`: form, density and pack unit for pre-filling; 3D printing and laundry products) and its Cost Source (`PRICE_SOURCES`: each source gives a `per_gram(density)` and a `per_piece()` price; `fixed` from pack price and size, `spoolman` the last price per gram read from the linked Spoolman Filament). A Material with pack unit `pcs` (`Material.by_piece`) is priced per piece, has no density or diameter and is never linked to Spoolman; its Line Items count `pcs` (`cost/material.py`'s `line_unit`, also when a Line Item's Material changes between pieces and grams: the quantity stays, re-priced).
- `spoolman.py`: Spoolman over its REST API (URL from the hub options, `CONF_SPOOLMAN_URL`). `Spoolman.async_filaments` reads every Filament with its price per gram (`filament.price ÷ weight`, else the newest priced spool) and syncs the linked Materials (`Catalog.async_sync_spoolman`: price, type, density, diameter, colour, vendor; without a price in Spoolman the last one stays); the tracker calls `async_update_prices` before freezing a Run; `async_create_material` / `async_link` create or link a Material. Any failure raises `SpoolmanUnreachable`.
- `catalog.py`: `Catalog`, the global catalogues (Materials so far) in the `catalog` Store. Every change is saved at once and announced by catalogue name (`async_listen`). Deleting a Material a Run's Line Item references (`LineItem.material_id`) archives it instead.
- `cost/`: the pure cost core (no HA imports): `consumption.py` (how much of any quantity between two moments: a meter interpolated between readings with dips and resets per ADR 0006 (`total`), a rate input by the left rule (`rate`), an amount spread evenly over a span (`spread`); `piecewise` switches models, e.g. when the average power changed), `pricing.py` (price segments from a price timeline whose gaps take the last valid price, and a consumed quantity's Line Item, `priced_line_item`), `electricity.py` (electricity's fallback without measurement: the average power `estimate`), `running_time.py` (running time without pauses), `slots.py` (Slot attribution: each loaded Slot report's share of running time, and its Material by type and colour, else the type's default), `material.py` (Material Line Items; `slot_line_items` makes one per Material and splits the measured total by share), `totals.py` (per-Device totals advanced by deltas).
- `tracker.py`: the Run engine for one Device (Status input → open, pause, end Run; reconciling after an outage; job changes, a Run named after its job without the file extension (`job_title`); the Program input's last valid value, trimmed, on the open Run (`_record_program`; a new Program never splits a Run, and the name follows it until the user renames the Run, `Run.follow_program`); each consumed quantity through its `Metering` (`metering.py`: the consumption-and-price building block, the same for every quantity: following the meter or rate input and the price, catching up from recorder history, the Line Item and the wait for a final report; only its fallback without measurement (a model such as the printer's average-power estimate; an amount for the whole Run, spread evenly over it, such as the Program Defaults' kWh or litres of the Run's Program (`_program_row`), method `program_default`; None as the amount for an empty quantity, which finalisation flags `default_missing`; None: no Line Item, as for water source none, which keeps a Water Line Item added by hand) and a rate input's gap rates come from the tracker; with `silent_meter_falls_back` (Devices with Program consumption) a meter without any valid reading up to the Run's end takes the fallback too, flagged `consumption_gap`); live refresh every minute and on each price report, finalisation; before freezing it reads Spoolman and flags `spoolman_unreachable` if that failed for a Run whose Material Line Items use a linked Material, and `spoolman_no_price` if such a Material has no price yet). The open Run keeps its price timelines (cleared at finalisation) and the average powers it used (`Run.average_powers`); a Device's new price or average power is appended from the moment the tracker starts with it (`_async_follow_device`), so it never recomputes what came before. A metered Run waits up to five minutes after its end for the meter's next report; `_end` returns a future done once the Run is finalised. While a Run is open, the Loaded slot input and the Slot entities build `Run.loaded_slots` (which Slot it printed from since when, with its reported type and colour; cleared at finalisation); the measured Material Line Items follow it, and finalisation flags `estimated_split` and `slot_fallback`. With the Doses capability, each Dose of the Device's panel settings that the Program Defaults' row of the Run's Program doses (the Default row when it has no Program or the Program no row; `dose_source` says which) becomes a Material Line Item (`_doses`, in Dose list order), recomputed from the settings until the Run is finalised (also on each settings change and Program change while it is open); a Cancelled or Failed Run with such Line Items gets `ended_early_defaults`. A Dose with a stock input is dosed by what that input lost instead (`Run.stocks`: per Dose its last level in g or ml and the decreases summed from the reading at the Run's start, refills ignored; cleared at finalisation; `device_inputs.stock_reading`), converted to the Material's pack unit through its density (`cost/material.in_pack_unit`); zero means not dosed, and without any usable report the row's amount applies and the Run gets `stock_input_unavailable`. The end waits up to five minutes for each stock input's next report, as for a meter. On start, `async_start` fills each unfinalised metered Run's missed reports from recorder history before applying the Status input. `async_create_run` makes a manual Run, final at once: electricity from recorder history if it covers the Run (`recorded.py`: the recorder was recording throughout and the meter had a reading at the start), else estimated from the average running power, else `entered` (not computed: the user types the kWh); the Material Line Item is left for the user to weigh.
- `timelines.py`: what the tracker keeps on a Run's `Timeline`, free of HA state: readings (`add_reading`, which flags `consumption_gap` and `meter_reset`), the price timeline (`add_price`), whether the meter reported the end (`has_final_report`) and the consumption model they make (`model`).
- `run_book.py`: all Runs in memory; every change goes through it so Stores, totals and listeners (`async_listen`) stay in step. User corrections go through `async_correct` (announced as `updated`, so `ended` never refires) and deletions through `async_delete` (announced as `deleted`; a listener on `RunChange.DELETED` is the place to remove a Run's files). `async_correct` also records a new image. Manual Runs go through `async_add` (announced as `created`, never `ended`).
- `images/`: Run images. `library.py` (`ImageLibrary`) stores an image on its Run (`async_add`: re-encoded by `encode.py`, a new Thumbnail or Snapshot replaces the old one), keeps the files under `files_path(hass)/images/<run id>/`, deletes a Run's files when it is deleted and removes files no Run refers to at startup. `capture.py` (`DeviceImages`, one per Device, driven by its tracker) copies the Thumbnail while a Run is open and takes the Snapshot when it ends. `view.py` serves the images to admins only (`image_info` gives the panel their URLs; the Run stores metadata only); `upload.py` takes the panel's multipart photo upload (`async_upload`: up to `UPLOAD_LIMIT` per Run, JPEG/PNG/WebP, all or none; `upload_rules` sends these limits in the Run detail as `uploads`, so the panel never repeats them). `async_delete` deletes one image; `Run.cover_id` is the picked Cover Image, which `Run.cover` checks first. The websocket commands for them are in `websocket/images.py`.
- `device_settings.py`: a Device's panel settings (Coin-op's own per-Device settings, set in the Devices tab), kept in the `device_settings` Store. A new setting is one entry in `FIELDS` (default and the schema a new value must pass); it then appears in `coinop/devices/list` and can be changed with `coinop/devices/update_settings`. Settings of removed Devices are dropped at setup. `doses` is the Dose list (`{id, material_id, stock?}` in order; the panel makes the ids; `stock` is `{entity_id, attribute, unit}`, the unit required with an attribute, only for Doses counted in g or ml) and `program_defaults` the amounts per Dose id and the optional `kwh` and `litres` per row (`{"default": {"doses": {...}, "kwh": ..., "litres": ...}, "programs": {...}}`; `program_row` is the row a Run's Program uses, else the Default row); a removed Dose's amounts are dropped. `async_listen` tells the trackers about every change.
- `store.py`: every Store (registered in `SCHEMAS`) and the file folder (`files_path`). `CoinOpStores` loads them together at setup (failing on missing or newer-major data, and through `parse` on data of another shape, with a `data_corrupt` repair issue), copies a Store to `<key>.bak` before a major migration and deletes everything when the hub entry is removed; `RunStore` writes Runs to `runs` and `live`. A new Store or file kind only registers there.
- `repairs.py`: the fix flow for missing data (restore guidance or a deliberate fresh start). `backup.py`: writes pending delayed saves before a backup.
- `ha_device.py`: Coin-op's own HA device per Device (registered at setup, linked to the printer's HA device), its `device_info`, and renames from the HA device page. Removing a Device ends its open Run as Unknown and finalises its Runs at once (`DeviceTracker.async_remove`, from `__init__.py` before the reload); `Run.device_name` always holds the Device's current name.
- `entity.py`: `DeviceEntity`, the base of every per-Device entity (device info, re-read on any change to one of the Device's Runs). `sensor.py`: totals, Current and Last Run cost, Flagged Runs. `event.py`: the Run event (`started`, and `ended` only from finalisation).
- `cost/rounding.py`: amounts rounded to the currency's decimals; subtotals and totals are sums of rounded amounts.
- `aggregates.py`: totals across Runs grouped by any of `DIMENSIONS` (kind, Device, month, Material, Outcome, Tag, Program) for the Overview and Analysis. Line Items are the facts: cost, grams and kWh sum the Line Items in a group, while Runs, running hours and Flagged Runs count each Run once per group it has a Line Item in, so Material and Tag groups overlap. `run_measures` is the same totals for a list of Runs (the deletion preview).
- `statement/`: the Cost Statement PDF (ADR 0005). `export.py` has the export options (`Options`; a new option is one field there, in the schema of `coinop/cost_statement/create` in `websocket/cost_statement.py` and in the panel's dialog) and `CostStatements`, which keeps each export's Runs and options for `EXPIRES` behind a token, plus the default Markup from the hub options (`CONF_MARKUP`). `view.py` serves `/api/coinop/cost_statement/{token}` to admins; the panel reaches it through the signed path `create` returns. On each download it renders the final Runs as they are now, ordered by start, in the executor. `document.py` lays out the PDF with fpdf2 (`render`: header, a section per Run with its Cover Image or a compact table, totals with Markup on the rounded subtotal, a footer on every page). The view passes the Cover Images' file paths (`covers`); `render` reads them and downscales each to a JPEG (`images/encode.jpeg`), leaving out a file it can't read. `keep_together` keeps a block on one page unless it is longer than a page. `text.py` holds the strings from `strings/{en,de}.json` (their own files, not HA translations) and formats money, numbers and dates for the language. `fonts/` has Noto Sans with its OFL licence.
- `panel.py`: registers the admin-only panel while the hub entry is loaded and serves the bundle at a URL that changes with its content.
- `websocket/`: the panel's backend API, one module per area (`runs.py`, `devices.py`, `materials.py`, `catalog.py`, ...). See [Websocket commands](#websocket-commands).

### Panel modules

- `src/coinop-panel.ts`: the element HA creates. It receives only `hass`, `narrow`, `route` and `panel`, keeps the Runs and the catalogue subscription, loads the Devices (again when the Devices tab opens or a Run of an unlisted Device changes) and routes by `route.path` (`""` Overview, `/run/<id>` Run page, `/<tab>` for each toolbar tab in `TABS`, led by `runs`; a new tab is one entry there, an icon in `ICONS`, a `tab.<name>` string and its view in `renderPage`). HA's `route` has no query, so the panel reads `location.search` itself on `location-changed` and `popstate`; it remembers the Runs tab's last query for the Runs tab link and the Run page's way back (`runsPath`). A Run page counts as part of the Runs tab. On desktop the tabs are icons with the tab's name as tooltip, led by the Overview's, and the title names the open tab; when `narrow` they are written out without the Overview, which the title leads back to. A Run whose `device_id` is not among the loaded Devices belongs to a removed Device (`deviceName` in `run-parts.ts`).
- `src/api.ts`: the websocket commands and the shapes they return. `src/hass.ts`: the part of `hass` the panel uses (`states` only for entities' friendly names on the Devices tab), plus `navigate` / `followLink` for in-app links.
- `src/overview.ts` (`<coinop-overview>`): tiles and charts from `coinop/aggregates/get` (drawn by `src/charts.ts` as inline SVG), the Runs running now and the 20 most recent Runs, with a link to all of them. The "Failed + cancelled" and "Flagged Runs" tiles and the month columns link to the Runs tab filtered (`runsPath`). `src/runs-page.ts` (`<coinop-runs-page>`): the Runs tab, with the list and the basket of selected final Runs (`selectedRuns()`, by start; its actions sit in the basket's `.actions` row, starting with "Cost Statement…" and ending with "Delete"; the basket sticks above the floating button while the list scrolls). It owns the selection, and the panel keeps it (lit `cache`) while other pages show, so the selection survives a visit to a Run page. Its filter and sort are the URL's query (`src/runs-query.ts`: `Filter`, `NO_FILTER`, `matches`, `programmed` (a Run of a Device with the `program` capability, or one with a Program: what the Program filter and table cover); `Sort`, `DEFAULT_SORT` (newest first, left out of the URL), `sorted`; `filterOf` / `sortOf` / `searchOf` / `runsPath` between them and the query); each change navigates, typing on in the name field replaces the history entry instead of adding one. The sort orders the gallery too. `src/run-list.ts` (`<coinop-run-list>`): filters, the Runs as gallery or table (a toggle; the choice is kept per browser in `localStorage` under `coinop-runs-view`, the gallery without one; on phones the table has fewer columns) and "Select all ended"; it reports `filter-changed` / `sort-changed` / `selection-changed`. A table row opens its Run unless the click was on its link or checkbox. `src/run-tile.ts`: a Run's tile (`runTile`, with a checkbox only when given `pick`) and `tileStyles`.
- `src/analysis-page.ts` (`<coinop-analysis-page>`): the Analysis tab's tables of totals by kind, Device, month, Material, Outcome, Tag and Program, each one `coinop/aggregates/get` grouping, read afresh whenever a Run changes. The Program table only shows with `programmed` Runs, grouping just those (`run_ids`), so printer Runs don't land in "No Program". Material comes from the `["kind", "material"]` grouping, so Electricity and Other Line Items don't count as "No Material"; the Tag table has no total row, since its groups overlap. The first cell of a Device, month, Outcome, Tag or Program row links to the Runs tab filtered by it (`runsPath`; "No tag" to untagged Runs, "No Program" to `noProgram`, "In progress" to open ones).
- `src/run-page.ts`, `src/devices-page.ts`, `src/materials-page.ts`, `src/tags-page.ts`, `src/templates-page.ts`: the other views, each read-only with its dialogs (see `src/fields.ts` below); `src/manual-run-dialog.ts`: the toolbar's "Manual Run" dialog; `src/dev-scenarios-dialog.ts`: the dev container's Scenario switcher, behind a round button at the bottom left, shown only when `hass.config.components` has `coinop_dev`; `src/statement-dialog.ts`: the basket's export dialog, which downloads the PDF with `download(path)` from `src/hass.ts` (built like HA's own `fileDownload`: an absolute link with `download` and `target="_blank"`, which the Android app hands to its download manager and the iOS app downloads or opens in the browser). The Runs tab passes the one filtered Tag (`.tag`) for the default title. The options except title and note are kept in `localStorage` (`coinop-statement-options`) after each statement made; every access is in `try`, and stored values that no longer fit are dropped. Every dialog is a `<coinop-dialog>` (`src/dialog.ts`): a native modal `<dialog>` that fires `cancel` on Escape or a click on the backdrop and focuses the content's `[autofocus]` element. Pages don't write one themselves: `formDialog()` is the dialog that edits (content, `error`, Cancel and the saving button, `ha-button.save` unless `action` names it; Enter in a field saves too) and `confirmDialog()` the confirmation of what can't be undone (`ha-button.confirm`). `src/run-parts.ts`: pieces several show (`deleteDialog` for the delete confirmation with what the sensor totals drop). `src/run-image.ts`: one Run image, fetched with `hass.fetchWithAuth` (the image views need authentication, which `<img src>` can't send) and shown from a blob URL, or the placeholder. `src/styles.ts`: shared styles on HA's theme variables. Fields are HA's filled text field at `ha-input`'s 56px; a select draws its own arrow. Buttons and icon buttons are HA's `ha-button`, `ha-icon-button` and `ha-svg-icon` with `@mdi/js` icons, used like HA's own pages do (cancel `appearance="plain"`, destructive `variant="danger"`, add actions `appearance="filled"` with `mdiPlus`); no other `ha-*` element is available to the panel (ADR 0007).
- `src/fields.ts`: the fields everything is edited with (ADR 0008). Pages show what is stored read-only; whatever is created or changed is a draft in a `formDialog()`, sent by its saving button (only the fields that changed, where the command takes a part) and kept open with `error` when the backend refuses it. `input()`, `numberInput()`, `select()`, `textarea()` and `checkbox()` are the controls (`onInput` follows the typing, `onChange` takes the value once the field is left and keeps Enter to itself); `field(label, control, { hint, name, group })` puts one under its label, `group` for several controls or the Tag input. A field is as wide as its dialog, and fields in a `<div class="field-row">` share a line evenly (`src/styles.ts`); no page sets a field's width, except for a small control beside a field of the same group (a colour picker, a pack unit). A field's unit goes inside it with `withUnit(control, unit)`, never beside it or into its label. ESLint refuses a raw `<input>`, `<select>` or `<textarea>` outside this module and the view controls (filters, pager, selection, upload) listed in `eslint.config.js`.
- `src/table.ts`: `table()`, the one table every page uses (a native `<table>` in a card that scrolls sideways when too wide and, where a page sets `--coinop-table-height` (the Analysis tab: about twelve rows), down under a head that stays; a paged table takes its `Pagination` controls as `pager`; pages render their own `<tr>`s, figures in `num` cells, row actions in an `actions` cell; `stacked` turns rows into cards on phones; a column with a `sort` key gets a header button with `aria-sort`, given `sort` and `onSort`: a click sorts ascending, the next reverses), with `tableStyles` for the page's styles. No page brings its own table styles.
- `src/pagination.ts`: `Pagination`, the controller of every list that can grow long (the Runs as gallery and table, Materials, Spoolman Filaments, Tags, Line Item Templates): `of(items)` is the current page, `controls(count, t)` the page size, range and page buttons under it, shown once a list has more than 25 items; `reset()` goes back to the first page (the Runs list on a new filter or sort). The page size is kept per browser in `localStorage` under `coinop-page-size`. A page with one adds `pagerStyles`.
- `src/localize.ts` with `src/translations/{en,de}.json` (flat keys): panel strings, chosen by `hass.language`, falling back to English. `src/format.ts`: money, dates and durations.

## Setup

Python is managed by [uv](https://docs.astral.sh/uv/); the system Python is not used. Home Assistant needs Python 3.14 (pinned in `.python-version`).

```sh
uv sync
```

This creates `.venv` with Home Assistant, the test harness ([pytest-homeassistant-custom-component](https://github.com/MatthewFlamm/pytest-homeassistant-custom-component)), ruff and mypy, pinned in `uv.lock`.

The panel needs Node.js (version in `frontend/.nvmrc`):

```sh
cd frontend
npm ci
npm run build    # or: npm run watch
```

Reload the browser after a rebuild; the bundle URL changes with its content when HA restarts or the entry reloads.

## Dev container

A Home Assistant in Docker with Coin-op and test data, logged in without a password (trusted networks; the port is bound to localhost only). It runs the HA version of `.venv` and keeps its config in `.dev/` (gitignored).

```sh
uv run scripts/devenv.py up [scenario]    # build the panel, (re)start, load a Scenario (default: few-runs),
                                          # then show HA's log until Ctrl+C stops it (--detach: keep running)
uv run scripts/devenv.py build            # rebuild the panel and reload Coin-op
uv run scripts/devenv.py restart          # after a change to the Python code
uv run scripts/devenv.py scenario long-history
uv run scripts/devenv.py logs | down
```

The `Makefile` has the same as `make dev`, `make dev-build`, `make dev-restart`, `make dev-scenario`, `make dev-logs` and `make dev-down`; `SCENARIO=long-history` picks the Scenario for `dev` and `dev-scenario`. While `make dev` runs in one terminal, the others go in a second one; a `dev-restart` doesn't end it.

Then open http://localhost:8124/coinop. The round flask button at the panel's bottom left (shown only when the `coinop_dev` integration is loaded) switches Scenarios too.

- `dev/configuration.yaml`: the container's configuration, with the printers' Status and job helpers (`input_select.<printer>_status`, `input_text.<printer>_job`) and the washing machine's (`input_select.washer_status`, `input_select.washer_program`, `input_number.washer_energy`, `input_number.washer_water`, `input_number.detergent_scale`); set them in HA to drive a live Run. The washing-machine Scenario replays its past loads by setting those helpers' states with past timestamps, so they go through the tracker like live ones.
- `dev/coinop_dev/`: the dev-only integration, mounted next to Coin-op. Its `load` service removes the hub entry, creates it afresh with the Scenario's Devices as subentries and fills it through Coin-op's own websocket commands on an in-process connection (`Api`), so the data takes the same path as a user's. Thumbnails are the only exception: no command adds one, so they go through `ImageLibrary`. A new Scenario is a fill function plus one entry in `SCENARIOS` (and in `services.yaml`). `tests/test_dev_scenarios.py` loads each one, so a changed command breaks the test, not the dev container.

## Test

```sh
uv run pytest                           # all tests, against the locked HA version
uv run pytest tests/test_config_flow.py -k second
uv run scripts/test_ha.py minimum -q    # also: stable, beta (each in its own .venv-<target>)
```

`scripts/test_ha.py` picks the harness release that pins the wanted HA version. The harness can lag behind a new HA release; the stable run then warns and tests the newest HA the harness supports. When raising the minimum HA version in `hacs.json`, update `MINIMUM_HARNESS_VERSION` in the script too (it fails if they disagree).

### Writing tests

## Release

The committed `manifest.json` keeps the placeholder version `0.0.0`; a release gets its version only from its tag.

1. Push a tag with the version, without a `v` prefix: `1.2.0`, or `1.2.0b1` / `1.2.0rc1` for a pre-release (releases before 1.0 are pre-releases).
2. `.github/workflows/release.yaml` builds the panel, runs `scripts/release.py` (which fails for any other tag) to zip `custom_components/coinop/` with the tag as the manifest's version, and creates a **draft** release with `coinop.zip` and generated notes, marked as a pre-release for `b` / `rc` tags.
3. Edit the notes (they become the release notes users see in Home Assistant; mention any raise of the minimum HA version) and publish the release. HACS and the Marketplace only offer published releases.

To check an asset locally: `make build VERSION=1.2.0b1` installs the panel's dependencies if `package-lock.json` changed, builds the panel and writes `dist/coinop.zip` (`VERSION` defaults to `0.0.0`).

## Conventions

- Everything in the repository is written in English.
- No user-facing text in Python: put it in `translations/en.json` and `translations/de.json` with identical keys (a test enforces this).
- Panel strings live in `frontend/src/translations/` with identical keys in every language. A term the backend translates too is listed in `SHARED_TERMS` in `tests/test_panel_translations.py`, which checks both sides read the same.
- Comments only for a non-obvious *why*.

### Websocket commands

- Named `coinop/<area>/<verb>` (`coinop/runs/list`, `coinop/runs/get`, ...), defined in `websocket/<area>.py` and listed in its `COMMANDS`; `websocket/__init__.py` registers every module's `COMMANDS`.
- Build each with `@command({vol.Required("type"): "coinop/...", ...})` from `websocket/command.py`: it makes the command admin-only, answers `not_loaded` while the hub entry isn't loaded, and passes the loaded `Coin-op` (sync or async handler).
- Results are objects (`{"runs": [...]}`, `{"run": {...}}`), never bare lists. Missing things answer `not_found`. Amounts are sent rounded with `cost/rounding.py`; the panel never adds amounts up itself.
- Subscriptions send their full state as the first event, then one event per change. Run changes reach them through the `SIGNAL_RUN_CHANGED` dispatcher signal, so a subscription survives reloads of the hub entry. Every `RunBook` change (`RunChange`) is forwarded as `{"change": ..., "run": summary}`, including `"deleted"`.
- Commands that change a Run answer with the Run in full (`{"run": ...}`), like `get`. Deleting is previewed: `delete_preview` and `delete` both answer `{"drop": ...}`, what the sensor totals lose.
- `coinop/catalog/subscribe` sends every catalogue first (`{"materials": [...], "tags": [...], "templates": [...]}`), then, after each change, the whole changed catalogue alone (e.g. `{"tags": [...]}`) through `SIGNAL_CATALOG_CHANGED`. A new catalogue adds its entry to `CATALOGUES` in `websocket/catalog.py` and announces its name from `Catalog`; the panel keeps one catalogue subscription and merges each event into what it has.
- `coinop/aggregates/get` takes `group_by` (a list of dimensions, none for one grand total), optionally limited to some Runs (`run_ids`: the gallery's, the basket's, failed + cancelled; `RunsTotal` in `src/runs-total.ts` reads one again when those Runs or their costs change) or to the Line Items of some Materials (`material_ids`, `null` for none: the Overview's other Materials), and answers `{"groups": [...]}`: each group's values (`month` as "YYYY-MM" in HA's time zone, `device_id` with `device_name`, `material_id` with `material_name`, `program`; `null` for none) followed by the totals `delete_preview` also sends. There are no groups without Runs. The panel reads them afresh after each Run change rather than subscribing.
- `coinop/devices/measured_suggestions` answers `{"suggestions": {"default": row, "programs": {name: row}}}`, each row `{"kwh": {"mean", "runs"}, "litres": {...}}` (a key without Runs left out): the mean measured or from-history quantity (as measured, not as the user overrode it) of the Device's finalised Completed Runs, per Program and for the Default row (Runs whose Program has no stored row). The Devices tab asks for it when the settings dialog of a Device with `program_consumption` opens and shows each mean beside its cell; only a click applies it.
- Fields of a catalogue entry travel nested (`{"type": "coinop/materials/create", "material": {...}}`), since a Material's `type` would clash with the command's.
