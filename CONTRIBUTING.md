# Contributing

## Layout

- `custom_components/coinop/`: the integration. Everything shipped to users lives here, including `translations/` (en and de, same keys) and `brand/`.
- `tests/`: backend tests, run inside a real Home Assistant test instance.
- `frontend/`: the sidebar panel (TypeScript + Lit). It builds into `custom_components/coinop/frontend/coinop-panel.js`, which is gitignored and built by CI.
- `scripts/test_ha.py`: runs the tests against the minimum, stable or beta Home Assistant release.
- `scripts/devenv.py` (with `make dev` shortcuts in the `Makefile`) and `dev/`: a local Home Assistant with test data (see [Dev container](#dev-container)).
- `scripts/release.py`: builds the release asset `coinop.zip` from a version tag (see [Release](#release)).
- `GLOSSARY.md`: domain terms; use them in code, tests and docs. Decisions go in `docs/adr/`.

### Backend modules

- `config_flow.py`: the hub entry and its options flow (`OPTIONS_SCHEMA`; `_async_validate` checks the input, e.g. the Spoolman URL against Spoolman's info endpoint; a new hub option is one field there plus its check and its `options.step.init` strings). Saving the options reloads the entry. `device_flow.py`: the Device subentry flow, one step per part of the Device's data (`device_type`, picked in Add Device's first step and never reconfigured; for the Device Type Other alone `type_name` and `capabilities`, asked for by the `other` step right after it, with the Type Names of the existing Other Devices as suggestions (see [Offering another choice for an Other Device](#offering-another-choice-for-an-other-device)), and again from an Other Device's reconfigure menu (see [Changing an Other Device later](#changing-an-other-device-later)); `printer_device_id` (the HA device of any Device Type, asked for by the `device` step, or by `device_without_profile` with its own text where no integration serves the Device Type), `status`, `mapping`, `job`, `images`, `program`, `consumption`, `price`, `water`, `water_price`). Where `profiles.candidates()` finds an HA device no Device follows yet, Add Device starts with Quick Start (`quick_start`; `quick_start_device_type`, shown only for a device whose kind can't be told and limited to the Device Types its integration serves; `quick_start_confirm`, which names the Device Type in HA's language, since a flow doesn't know its user's), which stores the profile's sections in the shape the steps write them (`UNUSED` for what the profile didn't find) and asks only for the meter and the prices. Steps are grouped into sections (`DeviceSubentryFlow._sections`, only those the Device's Capabilities include, which the flow resolves with `capabilities_of` from the data it has gathered, as the Device's configuration does): Add Device walks them in order, reconfigure offers them as a menu and returns to it after each; a new section is one entry there plus its menu label. Every section ends in `_section_done`, which hands the sections after it to `_walk`: Add Device goes on to the next and creates the Device after the last, reconfigure goes on only to a section named in `_walking` and else shows its menu again. So reconfigure can walk several sections before it returns to its menu, in Add Device's order: `_walk_before_menu` names them and starts at the first (Detect again's sections, and those a change of what an Other Device has brings). The consumption and price steps are shared by every consumed quantity (`_source_menu` and `_price_menu` for its two menus, `_async_meter_step`, `_async_price_entity_step`, ...; electricity keeps the plain step ids, water's are prefixed `water_`). A source menu offers `_sources(quantity)`: the quantity's `sources` without those whose Capability in `SOURCE_NEEDS` the Device lacks. Electricity comes from an energy meter, a power sensor, with `average_power` an estimate, with `program_consumption` "per Program", or from nowhere: source none (`NO_SOURCE` in `device_config.py`) is offered for electricity whatever the Capabilities, and for water. A section with source none holds just the source. It drops the quantity's price section (`price`, `water_price`) from Add Device and from the reconfigure menu, so a Device added with it has no price section; a price stored before stays in the data and is used again. Every source step ends in `_meter_done`, which names the price in `_walking` when the Device stores none, so a source picked in reconfigure after none walks on to its price. `profiles/`: the Integration Profiles, registered per integration (`INTEGRATIONS` in `profiles/__init__.py`, by integration domain; ADR 0004). Each group has its own module for its profiles and kind checks: `printers.py`, `appliances.py` and `ev_chargers.py`, each with the Device Types its integrations serve (`DEVICE_TYPES`); what profiles and kind checks are built from (`Integration`, `Find`, `KindCheck`, `NoDeviceType`, `found`, `entity_input` for an input read from an entity's state, `energy_source` for the electricity source on an energy meter, `mapping`, `always`) is in `base.py`, and the registry (an entry per integration, the printers' and EV chargers' made by `_printer` and `_ev_charger` with their group's Device Types and kind check), the lookup of entities by unique id, `detect` and `candidates` in `__init__.py`. `ev_chargers.energy_meter` picks a charger's electricity source among its lifetime and session counters (the lifetime one first unless `session_first`). An integration's entry (`Integration`) holds its name, the profile that finds its Device Inputs, the Device Types it serves and its kind check, which tells what an HA device is: a Device Type, `NoDeviceType.NOT_A_DEVICE` or `NoDeviceType.CANT_TELL`. WashData, Miele and Home Connect each serve the same five Device Types (`appliances.DEVICE_TYPES`): WashData tells them from the kind kept in its config entry (`washdata_kind`), Miele from the appliance type it writes as the HA device's model (`miele_kind`, any model not in `MIELE_KINDS` being no Device), Home Connect from the sensors it registers for an appliance's type alone (`home_connect_kind`, with its tables `HOME_CONNECT_KINDS` and `HOME_CONNECT_SHARED_KINDS`). The printer integrations serve the 3D printer alone and answer it for each of their devices (`printers.KIND`); an EV charger integration answers the EV charger the same way (`ev_chargers.KIND`). A kind check is called with the profile's `find`, the HA device and its config entry; see [Adding an appliance kind to a profile](#adding-an-appliance-kind-to-a-profile). Nothing outside the package reads the entries; it asks `known_integrations` (the names the HA device step shows for a Device Type, none for a Device Type no integration serves), `detect` and `candidates`. `detect` reads the Device's HA device and the devices linked to it (e.g. an ACE unit) from the registries and returns the sections it can fill (`status`, `mapping`, `job`, `images`, `program`, and for Miele the `consumption` and `water` meters), matching entities by unique id suffix; the profile is used whenever the HA device's integration serves the Device's Type, without asking the kind check. The flow keeps only the sections the Device Type has (`_fitting`, also for Quick Start's), so a washing machine's water meter never reaches a Device added as a Tumble dryer; the panel likewise shows a water source only with the `water` Capability. Add Device starts from them, and reconfigure's "Detect again" (offered only when `detect` knows the device) walks those sections pre-filled with them, except the meters (`METERS`), which it never touches. `candidates` is what Quick Start offers: the HA devices a profile finds a Status for, each a `Candidate` with the Device Types it can be added as (the one its kind check answers, or those its integration serves where the check can't tell; a device that is "not a Device" is left out). A new profile is one function in its group's module plus its integration's entry in `INTEGRATIONS`, under its group. `device_config.py` reads that data into a `DeviceConfig` and is the one place that answers what a Device has: `capabilities_of(data)` resolves a Device's Capabilities from its subentry data, from each shipped Device Type's set (`CAPABILITIES`, by Device Type key in the order Add Device lists them; see [Adding a Device Type](#adding-a-device-type)) or, for the Device Type Other, from the set the Device stores itself (ADR 0009), and `DeviceConfig.capabilities` and the flow both use it. `DEVICE_TYPES` is every Device Type in Add Device's order, Other last; `CHOICES` what an Other Device can have with the Capabilities each choice brings, `chosen_capabilities` the set a pick of them makes (with average power unless it has Program consumption), `stored_capabilities` that set as an Other Device stores it, `picked_choices` the way back from a stored set to the choices, `refused_combination` the one answer to whether a pick can be had together (it can't with Job and Material next to Program or Doses) and `TYPE_KEYS` the subentry keys that say what kind of Device it is, which are no section. The Capabilities (`Capability`) are job inputs, images, Material, Part Count, average power, Program, Doses, water, Program consumption (electricity and water source "per Program"), per-Run meters (meters that count each Run from 0, so a drop after its end is no `meter_reset`, and a meter without a value from the Run's start on whose first value is 0 no `consumption_gap`); code branches on these, never on the Device Type, and `coinop/devices/list` sends them to the panel as `capabilities`, with an Other Device's `type_name` beside its `type`. `device_inputs.py` reads Device Inputs from HA states and the entity registry, including a quantity's meter or rate readings converted to its units (`meter_reading`, e.g. kWh or W, units via HA's unit converters, else the user's conversion factor) and prices converted to `<currency>` per its unit (`price_reading`; `price_scale` understands the currency's code or symbol and sub-units like ct ÷ 100, per Wh/kWh/MWh). `quantities.py`: the consumed quantities (`Quantity`: Line Item kind, units of its meter and rate input, the unit prices are entered and shown in (`price_unit`, e.g. m³ for water priced per L) and a price entity's units (`price_units`), everything it can come from in its source menu's order (`sources`), the Device's section keys, its Program Defaults column (`default_key`) and display decimals (`shown_decimals`: `decimals`, and `small_decimals` for an amount under 1 of its unit, which is what shows a coffee's 0.04 L to the millilitre instead of as 0; it rounds the measured suggestions and the Cost Statement's quantities, and the panel's `SMALL_QUANTITY_DECIMALS` in `src/format.ts` mirrors it); `QUANTITIES` by Line Item kind); `ELECTRICITY` and `WATER` (meter in L, flow in L/min; Devices with the `water` Capability).
- `models.py`: `Run` and `LineItem`, free of HA types, with the JSON shape the Stores keep (`as_dict` / `from_dict`). A Run keeps a `Timeline` per consumed quantity (`Run.timelines`, by Line Item kind): the source section it started with (so a source change applies from the next Run), the price section it follows and, until finalised, its meter's `readings` and its `prices`. A Line Item's `quantity`, `unit_price` and `amount` are what counts; `LineItem.override` takes the user's values (an amount back-computes the unit price) and, on a computed Line Item (`is_computed`), keeps Coin-op's values in `computed` until `reset`. Which Line Items are live (`Run.locked`: computed ones until the Run is final), deletable (`Run.deletable`: all but a computed Electricity or Water one, so one entered by hand can go) and allow negative prices (`negative_prices`) is decided there too. A Dose's Material Line Item carries `dose_id` and `dose_source` (written only on those; `LineItem.from_defaults` marks a Water or Dose amount defaulted for a whole Run), and is computed like electricity. Which Flags a correction fixed (`Run.drop_fixed_flags`: `usage_missing` once every Material Line Item has a quantity, `material_missing` once each has a Material); `websocket/line_items.py` (`coinop/line_items/update`, `reset`, `add`, `delete`) applies these rules. `add` takes every kind: Other, Material, and Electricity or Water entered by hand (kWh or litres, method `entered`, empty until the user fills it in), of which a Run takes one each and is refused a second.
- `materials.py`: `Material`, free of HA types, with its built-in types (`MATERIAL_TYPES`: form, density and pack unit for pre-filling; 3D printing, laundry and dishwasher products and beverage ingredients), each form's pack unit when none is given (`USUAL_UNITS`, else grams) and its Cost Source (`PRICE_SOURCES`: each source gives a `per_gram(density)` and a `per_piece()` price; `fixed` from pack price and size, `spoolman` the last price per gram read from the linked Spoolman Filament). A Material with pack unit `pcs` (`Material.by_piece`) is priced per piece, has no density or diameter and is never linked to Spoolman; its Line Items count `pcs` (`cost/material.py`'s `line_unit`, also when a Line Item's Material changes between pieces and grams: the quantity stays, re-priced). A Material of a form in `UNLINKED_FORMS` (dishwasher products, beverage ingredients, Other) is never linked to Spoolman either (`Material.linkable`). The form Other (`MaterialForm.OTHER`) is for whatever fits no other form: it has no built-in types and no usual pack unit, so the user picks g, ml or pieces (grams when a new Material names none), and under it the panel suggests only the types of the Materials of that form and pre-fills nothing from a type (`hasBuiltInTypes` in `src/materials-page.ts`). A new Material form is one `MaterialForm` member, its entries there, and in the panel its key in `MATERIAL_FORMS` (`src/api.ts`), its usual pack unit and Spoolman rule in `src/materials-page.ts` and its `form.<key>` string in every language.
- `spoolman.py`: Spoolman over its REST API (URL from the hub options, `CONF_SPOOLMAN_URL`). `Spoolman.async_filaments` reads every Filament with its price per gram (`filament.price ÷ weight`, else the newest priced spool) and syncs the linked Materials (`Catalog.async_sync_spoolman`: price, type, density, diameter, colour, vendor; without a price in Spoolman the last one stays); the tracker calls `async_update_prices` before freezing a Run; `async_create_material` / `async_link` create or link a Material. Any failure raises `SpoolmanUnreachable`. At setup, while no URL is set and a Device has the Material Capability, `async_offer` (a background task) raises the fixable `spoolman_found` repair issue for the first Spoolman `async_find` gets an answer from: the Spoolman integration's `spoolman_url`, then each running Supervisor add-on with `spoolman` in its slug, at `http://<hostname>:<port>` for its Ingress port, its container ports and 7912 (an Ingress add-on's own proxy adds the Ingress path); otherwise it deletes the issue.
- `catalog.py`: `Catalog`, the global catalogues (Materials so far) in the `catalog` Store. Every change is saved at once and announced by catalogue name (`async_listen`). Deleting a Material a Run's Line Item references (`LineItem.material_id`) archives it instead.
- `cost/`: the pure cost core (no HA imports): `consumption.py` (how much of any quantity between two moments: a meter interpolated between readings with dips and resets per ADR 0006 (`total`), a rate input by the left rule (`rate`), an amount spread evenly over a span (`spread`); `piecewise` switches models, e.g. when the average power changed), `pricing.py` (price segments from a price timeline whose gaps take the last valid price, and a consumed quantity's Line Item, `priced_line_item`), `electricity.py` (electricity's fallback without measurement: the average power `estimate`), `running_time.py` (running time without pauses), `slots.py` (Slot attribution: each loaded Slot report's share of running time, and its Material by type and colour, else the type's default), `material.py` (Material Line Items; `slot_line_items` makes one per Material and splits the measured total by share), `totals.py` (per-Device totals advanced by deltas).
- `tracker.py`: the Run engine for one Device (Status input → open, pause, end Run; reconciling after an outage; job changes, a Run named after its job without the file extension (`job_title`); the Program input's last valid value, trimmed, on the open Run (`_record_program`; a new Program never splits a Run, and the name follows it until the user renames the Run, `Run.follow_program`); each consumed quantity through its `Metering` (`metering.py`: the consumption-and-price building block, the same for every quantity: following the meter or rate input and the price, catching up from recorder history, the Line Item and the wait for a final report; only its fallback without measurement (a model such as the printer's average-power estimate; an amount for the whole Run, spread evenly over it, such as the Program Defaults' kWh or litres of the Run's Program (`_program_row`), method `program_default`; None as the amount for an empty quantity, which finalisation flags `default_missing`; None: no Line Item) and a rate input's gap rates come from the tracker; a Run that started with source none is never asked for its fallback (`_fallback_of`), whatever the quantity and the Device Type, so it gets no Line Item, no Flag and no wait for that quantity, and keeps an Electricity or Water Line Item added by hand; a meter without any valid reading up to the Run's end flags the Run `consumption_gap` once it has ended, and with `silent_meter_falls_back` (Devices with Program consumption) takes the fallback too); live refresh every minute and on each price report, finalisation; before freezing it reads Spoolman and flags `spoolman_unreachable` if that failed for a Run whose Material Line Items use a linked Material, and `spoolman_no_price` if such a Material has no price yet). The open Run keeps its price timelines (cleared at finalisation) and the average powers it used (`Run.average_powers`); a Device's new price or average power is appended from the moment the tracker starts with it (`_async_follow_device`), so it never recomputes what came before. A metered Run waits up to five minutes after its end for the meter's next report; `_end` returns a future done once the Run is finalised. While a Run is open, the Loaded slot input and the Slot entities build `Run.loaded_slots` (which Slot it printed from since when, with its reported type and colour; cleared at finalisation); the measured Material Line Items follow it, and finalisation flags `estimated_split` and `slot_fallback`. With the Doses capability, each Dose of the Device's panel settings that the Program Defaults' row of the Run's Program doses (the Default row when it has no Program or the Program no row; `dose_source` says which) becomes a Material Line Item (`_doses`, in Dose list order), recomputed from the settings until the Run is finalised (also on each settings change and Program change while it is open); a Cancelled or Failed Run with such Line Items gets `ended_early_defaults`. A Dose with a stock input is dosed by what that input lost instead (`Run.stocks`: per Dose its last level in g or ml and the decreases summed from the reading at the Run's start, refills ignored; cleared at finalisation; `device_inputs.stock_reading`), converted to the Material's pack unit through its density (`cost/material.in_pack_unit`); zero means not dosed, and without any usable report the row's amount applies and the Run gets `stock_input_unavailable`. The end waits up to five minutes for each stock input's next report, as for a meter. On start, `async_start` fills each unfinalised metered Run's missed reports from recorder history before applying the Status input. `async_create_run` makes a manual Run, final at once: electricity from recorder history if it covers the Run (`recorded.py`: the recorder was recording throughout and the meter had a reading at the start), else estimated from the average running power, else `entered` (not computed: the user types the kWh), and none at all with electricity source none; the Material Line Item is left for the user to weigh.
- `timelines.py`: what the tracker keeps on a Run's `Timeline`, free of HA state: readings (`add_reading`, which flags `consumption_gap` and `meter_reset`; for a per-Run meter (`per_run`) a drop after the end is no reset, and a meter without a value from the Run's start on is only flagged by its first value, a gap unless that is 0, since a counter starting at 0 counted nothing before; a rate input without a value is a gap at once, and so is any meter that loses its value later in the Run), the price timeline (`add_price`), whether the meter reported the end (`has_final_report`) and the consumption model they make (`model`).
- `run_book.py`: all Runs in memory; every change goes through it so Stores, totals and listeners (`async_listen`) stay in step. User corrections go through `async_correct` (announced as `updated`, so `ended` never refires) and deletions through `async_delete` (announced as `deleted`; a listener on `RunChange.DELETED` is the place to remove a Run's files). `async_correct` also records a new image. Manual Runs go through `async_add` (announced as `created`, never `ended`). `unfinalised(device_id)` are a Device's Runs that can still change (an open one, or an ended one that waits for its inputs' last reports); the module's function of that name answers the same for any list of Runs.
- `images/`: Run images. `library.py` (`ImageLibrary`) stores an image on its Run (`async_add`: re-encoded by `encode.py`, a new Thumbnail or Snapshot replaces the old one), keeps the files under `files_path(hass)/images/<run id>/`, deletes a Run's files when it is deleted and removes files no Run refers to at startup. `capture.py` (`DeviceImages`, one per Device, driven by its tracker) copies the Thumbnail while a Run is open (a camera, or an image entity whose state is unknown at the Run's start, is fetched instead, again each minute until it gave a picture, then after `THUMBNAIL_REFRESH` and twice as long each time while the Run is open, keeping the latest) and takes the Snapshot when it ends. `view.py` serves the images to admins only (`image_info` gives the panel their URLs; the Run stores metadata only); `upload.py` takes the panel's multipart photo upload (`async_upload`: up to `UPLOAD_LIMIT` per Run, JPEG/PNG/WebP, all or none; `upload_rules` sends these limits in the Run detail as `uploads`, so the panel never repeats them). `async_delete` deletes one image; `Run.cover_id` is the picked Cover Image, which `Run.cover` checks first. The websocket commands for them are in `websocket/images.py`.
- `device_settings.py`: a Device's panel settings (Coin-op's own per-Device settings, set in the Devices tab), kept in the `device_settings` Store. A new setting is one entry in `FIELDS` (default and the schema a new value must pass); it then appears in `coinop/devices/list` and can be changed with `coinop/devices/update_settings`. Settings of removed Devices are dropped at setup. `doses` is the Dose list (`{id, material_id, stock?}` in order; the panel makes the ids; `stock` is `{entity_id, attribute, unit}`, the unit required with an attribute, only for Doses counted in g or ml) and `program_defaults` the amounts per Dose id and the optional `kwh` and `litres` per row (`{"default": {"doses": {...}, "kwh": ..., "litres": ...}, "programs": {...}}`; `program_row` is the row a Run's Program uses, else the Default row); a removed Dose's amounts are dropped. `async_listen` tells the trackers about every change.
- `store.py`: every Store (registered in `SCHEMAS`) and the file folder (`files_path`). `CoinOpStores` loads them together at setup (failing on missing or newer-major data, and through `parse` on data of another shape, with a `data_corrupt` repair issue), copies a Store to `<key>.bak` before a major migration and deletes everything when the hub entry is removed; `RunStore` writes Runs to `runs` and `live`, and `async_stored_runs` reads them back as setup would, without a loaded hub entry and without changing anything (None when a Store can't be read). A new Store or file kind only registers there.
- `repairs.py`: the fix flows, by issue id: missing data (restore guidance or a deliberate fresh start) and `spoolman_found` (checks the URL again and stores it in the hub options, which reloads the entry). `backup.py`: writes pending delayed saves before a backup.
- `ha_device.py`: Coin-op's own HA device per Device (registered at setup, linked to the printer's HA device), its `device_info`, and renames from the HA device page. Removing a Device ends its open Run as Unknown and finalises its Runs at once (`DeviceTracker.async_remove`, from `__init__.py` before the reload); `Run.device_name` always holds the Device's current name.
- `entity.py`: `DeviceEntity`, the base of every per-Device entity (device info, re-read on any change to one of the Device's Runs), and the `unique_id` its entities are registered under. `sensor.py`: totals, Current and Last Run cost, Flagged Runs; `NEEDS` names the totals only a Capability brings, and `async_remove_lost` removes those of a Capability an Other Device lost (see [Changing an Other Device later](#changing-an-other-device-later)). `event.py`: the Run event (`started`, and `ended` only from finalisation).
- `cost/rounding.py`: amounts rounded to the currency's decimals; subtotals and totals are sums of rounded amounts.
- `aggregates.py`: totals across Runs grouped by any of `DIMENSIONS` (kind, Device, month, Material, Outcome, Tag, Program) for the Overview and Analysis. Line Items are the facts: cost, grams and kWh sum the Line Items in a group, while Runs, running hours and Flagged Runs count each Run once per group it has a Line Item in, so Material and Tag groups overlap. `run_measures` is the same totals for a list of Runs (the deletion preview).
- `statement/`: the Cost Statement PDF (ADR 0005). `export.py` has the export options (`Options`; a new option is one field there, in the schema of `coinop/cost_statement/create` in `websocket/cost_statement.py` and in the panel's dialog) and `CostStatements`, which keeps each export's Runs and options for `EXPIRES` behind a token, plus the default Markup from the hub options (`CONF_MARKUP`). `view.py` serves `/api/coinop/cost_statement/{token}` to admins; the panel reaches it through the signed path `create` returns. On each download it renders the final Runs as they are now, ordered by start, in the executor. `document.py` lays out the PDF with fpdf2 (`render`: the header with the logo from `brand/` and the total, the breakdown of that total by cost kind as a bar with its legend in the panel's kind colours, a section per Run with its Cover Image or a compact table, with a Markup the totals that add it to the rounded subtotal, and a footer on every page, drawn last so it knows the page count). The view passes the Cover Images' file paths (`covers`); `render` reads them and downscales each to a JPEG (`images/encode.jpeg`), leaving out a file it can't read. `keep_together` keeps a block on one page unless it is longer than a page. `text.py` holds the strings from `strings/{en,de}.json` (their own files, not HA translations) and formats money, numbers and dates for the language. `fonts/` has Noto Sans with its OFL licence.
- `panel.py`: registers the admin-only panel while the hub entry is loaded and serves the bundle at a URL that changes with its content.
- `websocket/`: the panel's backend API, one module per area (`runs.py`, `devices.py`, `materials.py`, `catalog.py`, ...). See [Websocket commands](#websocket-commands).

### Panel modules

- `src/coinop-panel.ts`: the element HA creates. It receives only `hass`, `narrow`, `route` and `panel`, keeps the Runs and the catalogue subscription, loads the Devices (again when the Devices tab opens or a Run of an unlisted Device changes) and routes by `route.path` (`""` Overview, `/run/<id>` Run page, `/<tab>` for each toolbar tab in `TABS`, led by `runs`; a new tab is one entry there, an icon in `ICONS`, a `tab.<name>` string and its view in `renderPage`). HA's `route` has no query, so the panel reads `location.search` itself on `location-changed` and `popstate`; it remembers the Runs tab's last query for the Runs tab link and the Run page's way back (`runsPath`). A Run page counts as part of the Runs tab. On desktop the tabs are icons with the tab's name as tooltip, led by the Overview's, and the title names the open tab; when `narrow` they are written out without the Overview, which the title leads back to. A Run whose `device_id` is not among the loaded Devices belongs to a removed Device (`deviceName` in `run-parts.ts`).
- `src/api.ts`: the websocket commands and the shapes they return. `src/hass.ts`: the part of `hass` the panel uses (`states` only for entities' friendly names on the Devices tab), plus `navigate` / `followLink` for in-app links.
- `src/overview.ts` (`<coinop-overview>`): tiles and charts from `coinop/aggregates/get` (drawn by `src/charts.ts` as inline SVG), the Runs running now and the 20 most recent Runs, with a link to all of them. The "Failed + cancelled" and "Flagged Runs" tiles and the month columns link to the Runs tab filtered (`runsPath`). `src/runs-page.ts` (`<coinop-runs-page>`): the Runs tab, with the list and the basket of selected final Runs (`selectedRuns()`, by start; its actions sit in the basket's `.actions` row, starting with "Cost Statement…" and ending with "Delete"; the basket sticks above the floating button while the list scrolls). It owns the selection, and the panel keeps it (lit `cache`) while other pages show, so the selection survives a visit to a Run page. Its filter and sort are the URL's query (`src/runs-query.ts`: `Filter`, `NO_FILTER`, `matches`, `programmed` (a Run of a Device with the `program` capability, or one with a Program: what the Program filter and table cover); `Sort`, `DEFAULT_SORT` (newest first, left out of the URL), `sorted`; `filterOf` / `sortOf` / `searchOf` / `runsPath` between them and the query); each change navigates, typing on in the name field replaces the history entry instead of adding one. The sort orders the gallery too. `src/run-list.ts` (`<coinop-run-list>`): filters, the Runs as gallery or table (a toggle; the choice is kept per browser in `localStorage` under `coinop-runs-view`, the gallery without one; on phones the table has fewer columns) and "Select all ended"; it reports `filter-changed` / `sort-changed` / `selection-changed`. A table row opens its Run unless the click was on its link or checkbox. `src/run-tile.ts`: a Run's tile (`runTile`, with a checkbox only when given `pick`) and `tileStyles`.
- `src/analysis-page.ts` (`<coinop-analysis-page>`): the Analysis tab's tables of totals by kind, Device, month, Material, Outcome, Tag and Program, each one `coinop/aggregates/get` grouping, read afresh whenever a Run changes. The Program table only shows with `programmed` Runs, grouping just those (`run_ids`), so printer Runs don't land in "No Program". Material comes from the `["kind", "material"]` grouping, so Electricity and Other Line Items don't count as "No Material"; the Tag table has no total row, since its groups overlap. The first cell of a Device, month, Outcome, Tag or Program row links to the Runs tab filtered by it (`runsPath`; "No tag" to untagged Runs, "No Program" to `noProgram`, "In progress" to open ones).
- `src/run-page.ts`, `src/devices-page.ts`, `src/materials-page.ts`, `src/tags-page.ts`, `src/templates-page.ts`: the other views, each read-only with its dialogs (see `src/fields.ts` below). The Devices tab groups the Devices under their Device Type's heading (`device_type.<key>`), an Other Device under its `type_name` instead: one group per Type Name, apart from any Device Type's, in order of first appearance. A Device's card and settings dialog follow its `capabilities`: the Dose list comes with `doses`, the card's Program rows with `program`, and the Program Defaults table with either (with `program_consumption` a kWh column unless the electricity source is none and a litres column if the Device also has a water source other than none, a column per Dose with `doses`; no table without any such column; a hidden column's stored values are kept, and its measured suggestions hidden with it; its hint is the `device.program_defaults_hint*` string for the columns shown, then the one saying which row a Run uses: `…_rows`, or `…_default_row` on a Device without `program`, whose table is the Default row alone, with no Program rows and none to add, while rows stored for it are kept). The card shows the electricity price only for a source other than none, and `Device["ha_settings"]` has no `price` for a Device added with none. The Run page shows a kind's card as `shownKinds` says, but Electricity's only when the Run has an Electricity Line Item; without one it offers "Add electricity" in its place, in the dialog Water is added with (`CONSUMED_UNITS`); `src/manual-run-dialog.ts`: the toolbar's "Manual Run" dialog; `src/dev-scenarios-dialog.ts`: the dev container's test data dialog, which loads the Pieces picked (a `formDialog()` with `ha-button.load`), behind a round button at the bottom left, shown only when `hass.config.components` has `coinop_dev`; `src/statement-dialog.ts`: the basket's export dialog, which downloads the PDF with `download(path)` from `src/hass.ts` (built like HA's own `fileDownload`: an absolute link with `download` and `target="_blank"`, which the Android app hands to its download manager and the iOS app downloads or opens in the browser). The Runs tab passes the one filtered Tag (`.tag`) for the default title. The options except title and note are kept in `localStorage` (`coinop-statement-options`) after each statement made; every access is in `try`, and stored values that no longer fit are dropped. Every dialog is a `<coinop-dialog>` (`src/dialog.ts`): a native modal `<dialog>` that fires `cancel` on Escape or a click on the backdrop and focuses the content's `[autofocus]` element. Pages don't write one themselves: `formDialog()` is the dialog that edits (content, `error`, Cancel and the saving button, `ha-button.save` unless `action` names it; Enter in a field saves too) and `confirmDialog()` the confirmation of what can't be undone (`ha-button.confirm`). `src/run-parts.ts`: pieces several show (`deleteDialog` for the delete confirmation with what the sensor totals drop). `src/run-image.ts`: one Run image, fetched with `hass.fetchWithAuth` (the image views need authentication, which `<img src>` can't send) and shown from a blob URL, or the placeholder. `src/styles.ts`: shared styles on HA's theme variables. Fields are HA's filled text field at `ha-input`'s 56px; a select draws its own arrow. Buttons and icon buttons are HA's `ha-button`, `ha-icon-button` and `ha-svg-icon` with `@mdi/js` icons, used like HA's own pages do (cancel `appearance="plain"`, destructive `variant="danger"`, add actions `appearance="filled"` with `mdiPlus`); no other `ha-*` element is available to the panel (ADR 0007).
- `src/fields.ts`: the fields everything is edited with (ADR 0008). Pages show what is stored read-only; whatever is created or changed is a draft in a `formDialog()`, sent by its saving button (only the fields that changed, where the command takes a part) and kept open with `error` when the backend refuses it. `input()`, `numberInput()`, `select()`, `textarea()` and `checkbox()` are the controls (`onInput` follows the typing, `onChange` takes the value once the field is left and keeps Enter to itself); `field(label, control, { hint, name, group })` puts one under its label, `group` for several controls or the Tag input. A field is as wide as its dialog, and fields in a `<div class="field-row">` share a line evenly (`src/styles.ts`); no page sets a field's width, except for a small control beside a field of the same group (a colour picker, a pack unit). A field's unit goes inside it with `withUnit(control, unit)`, never beside it or into its label. ESLint refuses a raw `<input>`, `<select>` or `<textarea>` outside this module and the view controls (filters, pager, selection, upload) listed in `eslint.config.js`.
- `src/table.ts`: `table()`, the one table every page uses (a native `<table>` in a card that scrolls sideways when too wide and, where a page sets `--coinop-table-height` (the Analysis tab: about twelve rows), down under a head that stays; a paged table takes its `Pagination` controls as `pager`; pages render their own `<tr>`s, figures in `num` cells, row actions in an `actions` cell; `stacked` turns rows into cards on phones; a column with a `sort` key gets a header button with `aria-sort`, given `sort` and `onSort`: a click sorts ascending, the next reverses), with `tableStyles` for the page's styles. No page brings its own table styles.
- `src/pagination.ts`: `Pagination`, the controller of every list that can grow long (the Runs as gallery and table, Materials, Spoolman Filaments, Tags, Line Item Templates): `of(items)` is the current page, `controls(count, t)` the page size, range and page buttons under it, shown once a list has more than 25 items; `reset()` goes back to the first page (the Runs list on a new filter or sort). The page size is kept per browser in `localStorage` under `coinop-page-size`. A page with one adds `pagerStyles`.
- `src/localize.ts` with `src/translations/{en,de}.json` (flat keys): panel strings, chosen by `hass.language`, falling back to English. `src/format.ts`: money, quantities (decimals per unit, more for an amount under a litre), dates and durations.

## Setup

Python is managed by [uv](https://docs.astral.sh/uv/); the system Python is not used. Home Assistant needs Python 3.14 (pinned in `.python-version`).

```sh
uv sync
```

This creates `.venv` with Home Assistant, the test harness ([pytest-homeassistant-custom-component](https://github.com/MatthewFlamm/pytest-homeassistant-custom-component)), ruff and mypy, pinned in `uv.lock`.

The panel needs Node.js (version in `frontend/.nvmrc`):

```sh
cd frontend
npm ci
npm run build    # or: npm run watch
```

Reload the browser after a rebuild; the bundle URL changes with its content when HA restarts or the entry reloads.

## Dev container

A Home Assistant in Docker with Coin-op and test data, logged in without a password (trusted networks; the port is bound to localhost only). It runs the HA version of `.venv` and keeps its config in `.dev/` (gitignored).

```sh
uv run scripts/devenv.py up [preset]      # build the panel, (re)start, load a Preset (default: few-runs),
                                          # then show HA's log until Ctrl+C stops it (--detach: keep running)
uv run scripts/devenv.py build            # rebuild the panel and reload Coin-op
uv run scripts/devenv.py restart          # after a change to the Python code
uv run scripts/devenv.py scenario long-history
uv run scripts/devenv.py logs | down
```

The `Makefile` has the same as `make dev`, `make dev-build`, `make dev-restart`, `make dev-scenario`, `make dev-logs` and `make dev-down`; `SCENARIO=long-history` picks the Preset for `dev` and `dev-scenario`. While `make dev` runs in one terminal, the others go in a second one; a `dev-restart` doesn't end it.

Then open http://localhost:8124/coinop. The round flask button at the panel's bottom left (shown only when the `coinop_dev` integration is loaded) opens the test data dialog. It opens with the selection loaded last. From top to bottom: the Presets, a click on one of which fills in its Pieces and Options without loading them; All and None; the Options (history as a select, open Run as a checkbox); the Pieces under their group's Device Type, Devices with history first, then Quick Start Pieces. A group's heading has a checkbox that selects the whole group, or clears it when it is complete, shows whether all, some or none of its Pieces are picked and how many, and folds the group; the groups with a Piece picked start unfolded. Load sends the Pieces picked and the Options to the `load` service, or the Preset's name while a Preset's Pieces and Options are picked unchanged (changing a Piece or an Option makes the selection one's own), and opens the panel afresh; when loading fails, the dialog keeps them and says so.

The test data is made of **Pieces** that combine freely, each in a group (a Device Type key, `other` included) and one of two sections: a **Device with history** is a Device set up the way Add Device sets one up, with its Runs; a **Quick Start Piece** is an HA device of one integration with an Integration Profile, of one appliance kind, registered by that integration's stand-in, with no Coin-op Device yet. Two **Options** apply to every Piece picked: how much history each Device with history gets (`none`: the Device alone; `short`: a few weeks, around ten Runs; `long`: two years, and for the printers eight Materials with one archived, the Line Item Template on some Runs, Flags and Thumbnails), and whether each Device with history gets an open Run (`open_run`), started through its helpers once every Piece is filled, which setting its helpers ends. A **Scenario** is what gets loaded: a set of Pieces together with the Options. Loading always replaces everything, so the same Scenario gives the same data. **Presets** are named Scenarios, the names the CLI, the Makefile and the dialog take: `empty` (no Piece), `quick-start` (every Quick Start Piece), `few-runs` (the Prusa with short history), `printing-now` (the same with an open Run), `two-printers` (the Prusa and the Bambu with short history), `long-history` (both with long history), `washing-machine` and `irrigation` (each with short history). ## Test

```sh
uv run pytest                           # all tests, against the locked HA version
uv run pytest tests/test_config_flow.py -k second
uv run scripts/test_ha.py minimum -q    # also: stable, beta (each in its own .venv-<target>)
```

`scripts/test_ha.py` picks the harness release that pins the wanted HA version. The harness can lag behind a new HA release; the stable run then warns and tests the newest HA the harness supports. When raising the minimum HA version in `hacs.json`, update `MINIMUM_HARNESS_VERSION` in the script too (it fails if they disagree).

### Writing tests

- Drive Coin-op the way Home Assistant and the user do (config flows, entity states, websocket commands, the clock) and assert on what they can observe. Don't import internals.
- Each test gets a fresh HA instance through the `hass` fixture.
- Time is frozen and moved explicitly with the `clock` fixture from `tests/conftest.py`:

  ```python
  async def test_something(hass: HomeAssistant, clock: Clock) -> None:
      ...
      await clock.advance(minutes=5)  # fires every HA timer that is now due
      await clock.move_to(CLOCK_START + timedelta(days=1))
  ```

  `Clock` and `CLOCK_START` come from `tests/clock.py`.

- Schema changes: a minor bump only adds fields (read with a default), moving existing values into them through `minor_migrations` if needed (as 1.2 moved the electricity timelines into `Run.timelines`); a major bump adds a migration to the Store's `Schema` and a folder to `tests/fixtures/storage/` for the version just released (see `tests/test_migrations.py`). The hub entry and its Device subentries have their own version (`CoinOpConfigFlow.VERSION`/`MINOR_VERSION`), migrated by `async_migrate_entry` in `__init__.py`, with the stored shape of each released version in `tests/fixtures/config_entry/`.
- `tests/devices.py` sets up the hub (`add_hub`) and walks Add Device through the real flow (`add_device`, `walk_to_mapping` and `start_add_device` with `device_type=`, which chooses manual setup where Quick Start comes first; `tests/test_quick_start.py` has `pick` and `quick_start` for Quick Start itself, whose `device_type=` answers the Device Type step of a device whose kind can't be told; `add_printer` for a printer's HA device; `add_washing_machine` for a washing machine on `WASHER_STATUS` with `WASHER_ENERGY`, whose state the test sets first, and `program={...}` for the Program step's input, `water="meter"` / `"flow"` on `WASHER_WATER` with `water_price` per m³, `device_type=` for another Device Type with the same steps; ## Release

The committed `manifest.json` keeps the placeholder version `0.0.0`; a release gets its version only from its tag.

1. Push a tag with the version, without a `v` prefix: `1.2.0`, or `1.2.0b1` / `1.2.0rc1` for a pre-release (releases before 1.0 are pre-releases).
2. `.github/workflows/release.yaml` builds the panel, runs `scripts/release.py` (which fails for any other tag) to zip `custom_components/coinop/` with the tag as the manifest's version, and creates a **draft** release with `coinop.zip` and generated notes, marked as a pre-release for `b` / `rc` tags.
3. Edit the notes (they become the release notes users see in Home Assistant; mention any raise of the minimum HA version) and publish the release. HACS and the Marketplace only offer published releases.

To check an asset locally: `make build VERSION=1.2.0b1` installs the panel's dependencies if `package-lock.json` changed, builds the panel and writes `dist/coinop.zip` (`VERSION` defaults to `0.0.0`).

### Adding a Device Type

A shipped Device Type is a key, a Capability set and its names (the Device Type Other has no set: see [Offering another choice for an Other Device](#offering-another-choice-for-an-other-device)). Nothing branches on the key: flow steps, reconfigure sections, entities, event data, the tracker and the panel's parts all follow from the Capabilities.

1. **Key and Capabilities**: a `DEVICE_TYPE_*` constant in `const.py` and its entry in `CAPABILITIES` (`device_config.py`), placed where Add Device's Device Type step should list it; Other always comes last. A combination of Capabilities no Device Type had before needs tests of its own, and the code that reads Capabilities may need to learn it; a new Capability is a change of its own. The empty set is valid (the robotic mower): such a Device has what every Device has, a Status with its mapping and an electricity source (none among them) with its price, and nothing else.
2. **Names**: `selector.device_type.options.<key>` in `translations/en.json` and `de.json` (singular, for Add Device), and `device_type.<key>` in `frontend/src/translations/` (plural, the Devices tab's heading). The panel's `Device["type"]` is derived from those headings, so there is no list to extend in the panel. `tests/test_translations.py` and `tests/test_panel_translations.py` fail while a name is missing. Steps several Device Types share must not speak of one of them (`test_steps_shared_between_device_types_speak_of_none_of_them`). The images step is one of them, as an Other Device can have images: its printer example names what the image shows (a 3D model's preview), not the Device. The job step is another, as an Other Device with Job and Material sees it: it speaks of the Device and its job, and keeps the printer's cases as examples of what an entity reports (mm of filament, PLA, a multi-material unit). "Loaded slot" names one of its Device Inputs and is the one phrase the test lets pass despite "load". The estimate step is a third, as an Other Device without a Program sees it: it speaks of the Device and its Run, and keeps the printer's figures as an example (a desktop FDM device with a heated bed). The test leaves no step out. The panel is held to the same rule: only the 3D printers' heading may speak of a printer (`test_only_the_3d_printers_heading_speaks_of_a_printer` in `tests/test_panel_translations.py`, which reads the Cost Statement's strings too), since an Other Device with Job and Material shows what a printer's Runs show.
3. **Integration Profiles**: the key in `device_types` of every integration in `INTEGRATIONS` (`profiles/__init__.py`) that serves it, and in what its kind check answers (see [Adding an appliance kind to a profile](#adding-an-appliance-kind-to-a-profile)). A Device Type no integration serves needs nothing here: its HA device step is `device_without_profile`.
4. **Tests**: the list in `test_add_device_starts_with_the_device_type`; a module that walks its steps and reconfigure sections, drives a Run through entity states and reads the Devices command (`tests/test_dishwashers.py`; `tests/test_ovens.py` for a Device Type without water and Doses, `tests/test_robotic_mowers.py` for one without a Program); a recording of its `coinop/devices/list` in `tests/test_panel_contract.py` with a getter on `recorded`, and its row in `HEADINGS`, the Devices tab's headings in both languages (`frontend/test/devices.test.ts`).
5. **Docs**: its row in the README's Device Types table (what a Run records, which integrations pre-fill it), and the glossary where it brings a new example.

### Offering another choice for an Other Device

A Device of the Device Type Other has what its user picked in Add Device's `other` step. The step never says Capability: it offers choices named after things the glossary knows, each a toggle with a one-line explanation, and each choice brings one or more Capabilities. `CHOICES` in `device_config.py` is the one list of them; the step, the stored set and the panel follow from it.

| Choice | Key | Capabilities it brings |
| --- | --- | --- |
| Program | `program` | Program, Program consumption |
| Doses | `doses` | Doses |
| Water | `water` | water |
| Job and Material | `job` | job inputs, Material |
| Images | `images` | images |
| Part Count | `part_count` | Part Count |
| Meters count each Run from 0 | `per_run_meters` | per-Run meters |

A Device without Program consumption gets average power on top, so the electricity source menu offers either "per Program" or the estimate, never both. Doses go with a Program and without one: with it their amounts are per Program in the Program Defaults, without it they are the Default row alone, which every Run then takes (the choice brings no step either way; the Dose list is a panel setting). Water "per Program" is offered once Program and Water are both picked. Images and a Part Count need neither each other nor a job. Job and Material brings the job step (the job name, Material used, Slots and Loaded slot inputs), the default Material in the panel, a Material Line Item on every Run (measured, or left to fill in with its Flag), the Material used sensor and the grams in the `ended` event; a Run is named after its job.

**The one combination that is refused**: Job and Material together with Program, with Doses or with both. A Dose's Material Line Item would stand in for the Run's own one and its Flags, and the job and the Program would both name the Run. Every other mix of the seven choices is valid, none at all included. `refused_combination(choices)` in `device_config.py` is the one place that knows it: it answers the key of the `error` string that explains the refusal (`job_with_program_or_doses`), or None, and the `other` step shows that as its `base` error with the picks kept. Anything else that takes choices, such as changing them in reconfigure, asks the same function. The step's description states the rule and its reason before anything is picked, and that a Material Line Item can be added by hand on any Run whatever the Device has.

1. **The choice**: its entry in `CHOICES`, a key and the Capabilities it brings, placed where the step should list it ("Meters count each Run from 0" stays last). The key is the toggle's field name in the step. No choice may bring only Capabilities that another choice brings too: reconfigure shows a choice as picked when everything it brings is stored (`picked_choices`), and could not tell the two apart.
2. **Name and explanation**: `config_subentries.device.step.other.data.<key>` (the name) and `data_description.<key>` (one line saying what the Device gets) in `translations/en.json` and `de.json`. `test_what_an_other_device_can_have_is_named_and_explained` fails while one is missing or says Capability.
3. **Rules between choices** belong in `chosen_capabilities` when they decide a Capability (a Device without Program consumption gets average power) and in `refused_combination` when a combination is refused, with an `error` string that says why and the same words in the step's description.
4. **Tests**: `add_other_device(hass, entry, type_name=..., has=[<keys>], ...)` in `tests/devices.py` walks Add Device for the choices given; teach it the steps the new choice brings. Assert what the user sees (the steps, the Run's Line Items and Flags, the entities, `coinop/devices/list`), not the stored set. A recording of a Device with the choice in `tests/test_panel_contract.py` where the panel shows something new for it. Where the choice completes the mix of a shipped Device Type, a parity test in `tests/test_other_parity.py`. In `tests/test_other_changes.py`, the choice added to and removed from a Device that already has Runs; in `tests/test_other_entities.py`, the entities it brings created and removed with it.
5. **Docs**: its row in the table above, the choice where the README describes the Device Type Other, and the glossary where it changes what a term covers.

A Capability no Device Type had before is a change of its own, as for a shipped Device Type. An Other Device stores its Capabilities, not its choices, so changing what a choice brings later leaves the Devices already added as they are (ADR 0009).

### Changing an Other Device later

The reconfigure menu of an Other Device leads with `other`, the step Add Device asked: it shows the Type Name and the choices the stored Capabilities amount to (`picked_choices`), suggests the other Devices' Type Names and refuses the same combination. Only `picks_capabilities` decides that the entry is there, so a shipped Device Type's menu has none. The Device Type is never asked again.

Submitting the step stores the Type Name and the new Capabilities in the flow's data and fits the sections to them (`_async_fit_sections`). Nothing reaches the Device before Save, so leaving the flow halfway changes nothing.

1. **Dropped**: the sections of a Capability the Device no longer has (`NEEDS`), and a stored source it is no longer offered (`_sources`, which the source menus show too: a quantity's `sources` without those whose Capability in `SOURCE_NEEDS` the Device lacks): the estimate once it has a Program, "per Program" for electricity or water once it has none. A power sensor's `running_power` goes with average power. The tracker and the image capture read the sections, not the Capabilities, so a section that stayed would go on working.
2. **Walked**: every section the Device has and stores nothing for, in Add Device's order, before the menu comes back: a new choice's sections and each dropped source (whose price is still stored and isn't asked again). A choice that brings a section must therefore list it in `NEEDS`; one that changes which sources are offered belongs in `SOURCE_NEEDS`.
3. **Kept**: everything else, as it is. That includes the panel settings in the `device_settings` Store (Dose list, Program Defaults, default Material), which nothing reads while the Device lacks their Capability and which apply again when it returns; `coinop/devices/update_settings` keeps refusing a Dose list on a Device without Doses. Ended Runs are frozen and never touched.

The step is refused, and so is Save after a change of the Capabilities, while the Device has a Run that isn't final (`_async_refusal`, which answers the abort reason; `RunBook.unfinalised` are those Runs): an open one, or one that ended and waits for its meters' last reports. A Run is computed from what its Device has until it is finalised, so it would change what it records halfway. Both abort with `abort.run_open` and save nothing. While the hub entry isn't loaded there is no Run book to ask, and a stored Run goes on when the entry loads again, so the flow reads the Stores as setup would (`async_stored_runs` in `store.py`): a Run of the Device that isn't final aborts with `abort.run_open_not_loaded`, Stores it can't read (missing, newer or of another shape) with `abort.runs_unreadable`, and a Device without such a Run is changed as usual. Save reloads the hub entry, so the Device's tracker starts over with the new Capabilities and the next Run records what the Device has then.

The Device's entities follow at Save. The sensors of a Capability the Device no longer has leave the entity registry (`async_remove_lost` in `sensor.py`, which the `save` step calls with the Capabilities that were stored and no longer are): the two water sensors without water, Material used without Material. The reload then creates the sensors a new Capability brings, as every setup does from `NEEDS` in `sensor.py`, so a sensor that comes with a Capability needs only its entry there.

- **What is removed** is found by what the sensor platform registered it as: a sensor of Coin-op with the unique id of that Device and that `NEEDS` key (`unique_id` in `entity.py`). A sensor the user renamed or disabled goes too; another Device's entities, the Run event, the sensors every Device has and anything another integration registered can't match.
- **Only Save removes.** No setup and no reload takes an entity out of the registry, whatever the Device lacks. A Device of a shipped Device Type therefore never loses one, as no Save changes its Capabilities, not even after a release changed its Device Type's set; and a change saved while the hub entry isn't loaded (which takes a Device without a stored Run that isn't final) takes its sensors along all the same.
- **A sensor that comes back** counts every ended Run again, as the totals are derived from the Runs. Home Assistant keeps a removed entity's registry entry aside and hands the returning sensor its entity id, name and other settings back; Coin-op does nothing for or against that.

### Adding an appliance kind to a profile

An integration's entry in `INTEGRATIONS` (`profiles/__init__.py`) says which Device Types it serves and how it tells which of them an HA device is. Teaching an integration a kind is an edit to that entry; the profile that finds its Device Inputs stays as it is, and nothing is stored about the kind (ADR 0004).

1. **Read the integration's source** for what it registers for that kind only: a value on its config entry (WashData's `device_type`), the HA device's model, or an entity only that kind gets. Note the exact strings and where they come from; a kind the integration can't tell apart is "can't tell", never a guess.
2. **Device Types served**: the Device Type's key in the entry's `device_types`. That alone names the integration in the HA device step and makes manual setup and Detect again pre-fill from it for that Device Type, whatever its kind check says.
3. **Kind check**: the entry's `kind`, called as `kind(find, device, config_entry)` for a device its profile found a Status for. It answers a Device Type's key, `NoDeviceType.CANT_TELL` (Quick Start asks for the Device Type, among `device_types`) or `NoDeviceType.NOT_A_DEVICE` (Quick Start leaves the device out). `find(platform, *suffixes)` finds an entity by unique id suffix as in the profiles, the suffixes in their order; `find(..., disabled=True)` also finds one that is disabled, as entities an integration registers disabled by default are, `start=True` matches the start of the unique id instead (an integration whose ids start with the key, such as OctoPrint's and Wallbox's), and `exclude=` passes over ids ending in it (a longer key ending alike, such as Moonraker's lifetime filament total). `find` also looks at the HA devices linked to the chosen one (a multi-material unit), unless the entry sets `linked_devices=False` for an integration whose linked devices are Devices of their own (OCPP's connectors). Keep the strings in one table next to the check in its group's module (`WASHDATA_KINDS`, `MIELE_KINDS`, `HOME_CONNECT_KINDS` in `profiles/appliances.py`), and decide what an unknown string answers. Where the kind is told from entities, use ones the integration registers for the appliance's type alone, not from what the appliance reports, and that Coin-op's minimum Home Assistant version registers too: a kind it can't tell there must come out as "can't tell".
4. **Stand-in**: the integration's description in `dev/coinop_dev/stand_ins/appliances.py` registers the appliance the way the integration does, with exactly what the check reads (config entry data and options, model, entities with their `disabled_by`) and a plausible state for each entity; the integration's fixture in `tests/registry.py` registers from it. The dev container offers the kind through a Quick Start Piece: for a static stand-in, a `StaticPiece` whose `registration` is that description, so the stand-in follows from it with no code of its own (see [Dev container](#dev-container)).
5. **Tests** in the integration's test module (`tests/test_appliance_kinds.py` for WashData, Miele and Home Connect, else its own, such as `tests/test_lg_thinq.py`), through Quick Start: each kind is added as its Device Type with Status, mapping and Program pre-filled; a kind that can't be told shows `quick_start_device_type` with the Device Types served; a kind that is no Device Type isn't offered. In `tests/test_washer_profiles.py`: the Device Type's row in `test_the_ha_device_step_names_the_integrations_known_for_the_device_type`; manual setup and Detect again for a Device Type the integration newly serves go in its test module.
6. **Docs**: the integration in the "Pre-filled for" column of the README's Device Types table and what it tells under [Quick Start](README.md#quick-start), and ADR 0004 where it lists what each integration serves.

### Websocket commands

- Named `coinop/<area>/<verb>` (`coinop/runs/list`, `coinop/runs/get`, ...), defined in `websocket/<area>.py` and listed in its `COMMANDS`; `websocket/__init__.py` registers every module's `COMMANDS`.
- Build each with `@command({vol.Required("type"): "coinop/...", ...})` from `websocket/command.py`: it makes the command admin-only, answers `not_loaded` while the hub entry isn't loaded, and passes the loaded `Coin-op` (sync or async handler).
- Results are objects (`{"runs": [...]}`, `{"run": {...}}`), never bare lists. Missing things answer `not_found`. Amounts are sent rounded with `cost/rounding.py`; the panel never adds amounts up itself.
- Subscriptions send their full state as the first event, then one event per change. Run changes reach them through the `SIGNAL_RUN_CHANGED` dispatcher signal, so a subscription survives reloads of the hub entry. Every `RunBook` change (`RunChange`) is forwarded as `{"change": ..., "run": summary}`, including `"deleted"`.
- Commands that change a Run answer with the Run in full (`{"run": ...}`), like `get`. Deleting is previewed: `delete_preview` and `delete` both answer `{"drop": ...}`, what the sensor totals lose.
- `coinop/catalog/subscribe` sends every catalogue first (`{"materials": [...], "tags": [...], "templates": [...]}`), then, after each change, the whole changed catalogue alone (e.g. `{"tags": [...]}`) through `SIGNAL_CATALOG_CHANGED`. A new catalogue adds its entry to `CATALOGUES` in `websocket/catalog.py` and announces its name from `Catalog`; the panel keeps one catalogue subscription and merges each event into what it has.
- `coinop/aggregates/get` takes `group_by` (a list of dimensions, none for one grand total), optionally limited to some Runs (`run_ids`: the gallery's, the basket's, failed + cancelled; `RunsTotal` in `src/runs-total.ts` reads one again when those Runs or their costs change) or to the Line Items of some Materials (`material_ids`, `null` for none: the Overview's other Materials), and answers `{"groups": [...]}`: each group's values (`month` as "YYYY-MM" in HA's time zone, `device_id` with `device_name`, `material_id` with `material_name`, `program`; `null` for none) followed by the totals `delete_preview` also sends. There are no groups without Runs. The panel reads them afresh after each Run change rather than subscribing.
- `coinop/devices/measured_suggestions` answers `{"suggestions": {"default": row, "programs": {name: row}}}`, each row `{"kwh": {"mean", "runs"}, "litres": {...}}` (a key without Runs left out): the mean measured or from-history quantity (as measured, not as the user overrode it) of the Device's finalised Completed Runs, per Program and for the Default row (Runs whose Program has no stored row). The Devices tab asks for it when the settings dialog of a Device with `program_consumption` opens and shows each mean beside its cell; only a click applies it.
- Fields of a catalogue entry travel nested (`{"type": "coinop/materials/create", "material": {...}}`), since a Material's `type` would clash with the command's.
